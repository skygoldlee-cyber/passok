# 프로젝트 평가지표 — 범용 프레임워크와 측정 규약

> **문서 ID**: DOC-REF-15
> **범위**: platform · 판본: none
> **관련 SPEC ID**: 해당 없음 (평가 방법론 — 이 저장소의 측정 경로는 §8, 실측 사례는 §9)
> **대상**: 이 저장소(또는 다른 프로젝트)의 상태를 정량 평가하는 사람

## 1. 목적과 원칙

평가지표는 "프로젝트가 건강한가"에 대한 질의응답 도구다. 원칙 세 가지:

1. **스냅샷보다 추세** — 단일 시점 수치보다 변화율(커버리지 증감, 부채 누적 속도)이 신호다.
2. **정합 지표와 가치 지표를 구분** — "문서↔코드 일치" 같은 내부 정합은 부패를 막지만 사용자 가치를 증명하지 않는다. 이 문서는 가치 계열을 별도 버킷(§2.6)으로 둬서, 두 계열을 합산 평균하지 못하게 한다 — 합치면 높은 정합 점수가 낮은 가치를 은폐한다.
3. **측정되는 것은 최적화된다**(Goodhart) — 지표를 게이트로 쓰면 게이트 통과 자체가 목표가 된다. 지표는 진단용이며 목표는 제품이다.

## 2. 지표 체계 — 7개 버킷

표의 "측정 예시"는 특정 생태계 도구의 이름이 아니라 측정 가능한 경로다. 실제 도구는 §7의 치환 규칙으로 프로젝트 생태계에 맞춘다.

### 2.1 규모·생산성 (규모의 무게)

| 지표 | 정의 | 측정 예시 | 해석 |
|------|------|-----------|------|
| 소스 LOC / 파일 수 | 언어별 라인 집계 | 라인 집계 도구 | 절대 수보다 최대 파일 크기·모듈 분포가 중요 |
| 테스트/소스 비율 | 테스트 산출물 LOC ÷ 소스 LOC | 디렉터리별 집계 | 극단값(0 근접·소스의 수 배)만 경계 신호 — 절대 정상 범위는 프로젝트 유형에 따라 크게 달라 보편 기준을 두지 않는다 |
| 인프라 코드 비율 | 빌드·배포·검증 도구 코드 ÷ 소스 | 디렉터리별 집계 | 인프라가 앱 본체의 수십 %면 그 자체가 유지비 리스크 — 임계는 자체 추세로 |
| 변경 속도 | 기간당 커밋·PR 수 | VCS 이력 | 프로젝트 간 비교 불가(커밋 단위가 제각각) — **동일 프로젝트 내 추세**와 "작성자 기억에만 있는 맥락"의 프록시로만 사용 |
| 기여자 수 / 버스 팩터 | 의미 있는 변경을 한 기여자 수 | VCS 이력 | 1이면 §2.5(지식 보존)가 선택이 아니라 필수 |

### 2.2 품질·검증 (오류가 잡히는가)

| 지표 | 정의 | 측정 예시 | 해석 |
|------|------|-----------|------|
| 테스트 수(계층별) | 단위/통합/E2E 분리 집계 | 러너 리포트 | 피라미드 형태인가 — 상위 계층만 많으면 피드백이 느림 |
| 테스트 실통과 | 최근 N회 실행 성공률 | CI 이력·로컬 실행 | 실행 기록이 없는 테스트 수는 장식 |
| 커버리지 | 행·분기·함수 커버리지 | 커버리지 도구 병합 | 절대치보다 핵심 경로 커버와 추세. 단조 증가 래칫이 회귀 방지 |
| 정적 분석 위반 | 린트·타입 오류/경고 수 | 린터·타입체커 | 경고 0 정책 유지 여부 + 억제 주석(suppress/disable) 수 = 규약 우회량 |
| 변이 테스트 점수 | 의도적 변이 도입 시 테스트 발견율 | 변이 테스트 도구 | 단언이 실제로 결함을 잡는지의 직접 지표 — 수가 아니라 실효성 |
| 금지 패턴 잔존 | TODO/FIXME·디버그 코드·미사용 자산 | 텍스트 스캔·정적 분석 | 부패 축적량의 직접 측정 |

### 2.3 유지보수성 (변경 비용)

| 지표 | 정의 | 측정 예시 | 해석 |
|------|------|-----------|------|
| 최대 파일·순환 복잡도 | 파일 크기·함수 복잡도 상위값 | 정적 분석 | 큰 파일 하나가 수정의 중심이면 분해 후보 |
| 의존성 개수·신선도 | 직접 의존 수·업데이트 지연 | 매니페스트·audit | 의존이 적을수록 공급망 리스크↓ — 고정(pin) 여부와 함께 본다 |
| 코드↔선언 정합 | 설정·선언부가 실제 동작을 반영하는가 | 도메인별 정합 검증(있으면) | 선언과 동작의 괴리는 "보이는 상태 ≠ 실제 상태" 버그의 온상 |
| 생성물 신선도 | 커밋된 생성물 ↔ 원본 일치 | 재빌드 후 diff | 생성물을 커밋하는 저장소만 해당 — 없으면 N/A |

### 2.4 운영·배포·전달 (실제로 사는가 · 팀이면 흐르는가)

| 지표 | 정의 | 측정 예시 | 해석 |
|------|------|-----------|------|
| 배포 경로 단일성 | 프로덕션 진입점 개수 | 배포 설정 | 복수 경로 = 가드 우회 가능 |
| 배포 후 검증 | 배포 직후 자동 스모크 존재 | 배포 스크립트 | 배포 성공 ≠ 앱 동작 |
| 롤백 경로 | 이전 버전 복원 절차 유무·검증 | 문서+실행 이력 | 실행해본 적 없는 롤백은 미검증 |
| 장애 이력·MTTR | 인시던트 기록과 복구 시간 | 인시던트 로그 | 기록 부재는 무장애가 아니라 미관측일 수 있음 |
| **DORA 4지표** (팀) | 배포 빈도·변경 리드타임·변경 실패율·복구 시간 | VCS+배포+인시던트 결합 | 다인 프로젝트의 전달 성숙도 표준 — 솔로는 N/A 처리 가능 |
| 리뷰 커버리지·PR 리드타임 (팀) | 리뷰 경유 변경 비율·오픈→머지 시간 | PR 이력 | 솔로 프로젝트는 N/A — 리뷰 없는 직접 커밋이 전부면 §2.5 리허설이 대체 검증층 |

### 2.5 지식 보존·온보딩 (맥락이 복원되는가)

| 지표 | 정의 | 측정 예시 | 해석 |
|------|------|-----------|------|
| 결정 기록 밀도 | 주요 결정당 대안·근거 기재율 | ADR·설계 문서 | 수보다 "기각된 대안" 기록 유무가 핵심 — 재제안 방지 |
| 운영 절차 커버리지 | 운영 시나리오 대비 문서화 비율 | 런북 목록 vs 시나리오 | 평시 절차보다 "깨졌을 때" 절차 유무 |
| 문서 신선도 | 문서가 코드와 다른 지점 수 | 정합 검증·수동 샘플 | stale 문서는 문서가 아니라 함정 |
| **낯선 눈 리허설** | 무컨텍스트 작업의 성공률·막힘 수 | 새 기여자/세션에 실작업 부여 | 지식 보존의 실증 지표 — 문서 존재 ≠ 문서 유효 |
| 온보딩 시간 | 신규 기여자의 첫 성공적 변경까지 시간 | 리허설 계측 | 리허설로 주기 측정 |

### 2.6 가치·사용 (사용자에게 효과가 있는가) — 정합 지표와 분리 평가

§2.1~2.5는 전부 내부 엔지니어링 지표다. 이 버킷이 없으면 "모든 게이트 통과 + 아무도 쓸 수 없는 앱"이 양호로 판정된다.

| 지표 | 정의 | 측정 예시 | 해석 |
|------|------|-----------|------|
| 핵심 시나리오 성공률 | 사용자 주요 과업의 end-to-end 성공 | E2E 시나리오·수동 검수 | 유닛 통과와 무관하게 "쓸 수 있는가"의 직접 지표 |
| 런타임 오류율 | 사용자 환경에서 발생한 오류 수/비율 | 오류 텔레메트리·로그 | 텔레메트리가 없으면 이 지표 자체가 공백 = 리스크 |
| 실사용 | 활성 사용자·기능별 사용률·유지율 | 분석 도구·로그 | B2C/B2B는 필수 — 사내·개인용은 N/A 가능 |
| 성능 | 지연·번들 크기·렌더 시간·인프라 비용 | 계측·예산 검사 | 사용자 경험의 일부이자 비용 — 예산(budget) 없으면 추세만이라도 |
| 회귀 신고율 | 릴리스당 사용자 신고·롤백 건수 | 이슈·배포 이력 | 변경 품질의 최종 심판 |

### 2.7 보안·컴플라이언스

| 지표 | 정의 | 측정 예시 | 해석 |
|------|------|-----------|------|
| 의존성 취약점 | 알려진 CVE가 있는 의존 수 | audit·스캐너 | 심각도별 잔존과 노출 경로 — "해결됨"보다 "재발 방지 체계" 유무 |

| 규제·라이선스 | 데이터 규제 해당 여부·의존 라이선스 | 라이선스 스캔·SBOM | 개인정보·결제 등 다루면 별도 감사 필요 |

### 2.8 프로젝트 유형별 프로필 — 어디에 무게를 둘 것인가

버킷 전체를 같은 무게로 평가하지 않는다. 유형별 핵심 축과 고유 추가 지표:

| 유형 | 핵심 버킷 | 유형 고유 지표 |
|------|-----------|----------------|
| 웹 앱·서비스 | 가치·사용 / 운영·배포 / 보안 | 위 표 기본 세트로 충분 |
| 라이브러리·패키지 | 품질·검증 / 유지보수 / 보안 | **공개 API 안정성·semver 준수·breaking change 이력·하위호환 테스트** — 배포 버킷은 릴리스 절차로 치환 |
| ML·데이터·트레이딩 | 가치·사용 / 품질·검증 | **모델 성능 지표·학습↔운영 데이터 드리프트·백테스트↔실적 괴리·재현 가능한 학습 파이프라인** — 유닛 커버리지는 핵심 리스크를 거의 잡지 못해 가중치를 낮춤 |
| 데스크톱·CLI 도구 | 품질·검증 / 유지보수 / 지식 보존 | 설치·실행 성공률·플랫폼별 동작 — 배포 버킷은 배포 채널(스토어·패키지 매니저)로 치환 |
| 인프라·내부 도구 | 운영·배포 / 보안 / 지식 보존 | 복구 시간·변경 실패율이 상위 지표 — 가치 버킷은 내부 사용자 만족으로 치환 |

## 3. 평가 프로세스

1. **측정** — §2 지표 중 자동 수집 가능한 것부터. 수동 측정은 재현 명령을 함께 기록한다.
2. **해석** — 각 지표에 "정상 범위"가 아니라 "이 프로젝트 문맥의 의미"를 붙인다 (예: 솔로 프로젝트의 기여자 1은 결함이 아니라 전제).
3. **리스크 변환** — 지표 → "무엇이 깨질 수 있는가" 문장으로. 숫자 자체는 행동을 유도하지 못한다.
4. **우선순위** — 영향×확률로 정렬. 측정이 안 되는 리스크는 리허설·탐색으로 실증한다.
5. **재평가 주기** — 주요 변경 후, 또는 분기 1회. 평가 보고서 자체도 문서로 남겨 추세를 만든다.

## 4. 함정 — 지표 해석에서 자주 틀리는 것

- **테스트 수 = 품질** — 수천 개가 통과해도 "해당 단언이 안 깨졌다"는 뜻일 뿐이다. 변이 점수 없이는 단언 밀도 미지수.
- **커버리지 상한 효과** — 어떤 수치든 제외된 나머지의 내용이 의미를 정한다. 측정 불가 모듈이 분모에서 빠졌는지 먼저 확인.
- **문서 수 = 문서화** — stale 문서는 음의 가치. 정합 검증 없이 문서 수를 세면 부패를 가산한다.
- **게이트 수 = 강함** — 게이트 자체의 유지비와 오탐률을 같이 본다. 오탐이 쌓이면 우회가 관례가 되어 게이트가 무의미해진다.
- **높은 정합 점수 = 높은 품질** — 내부 정합은 자기 일관성일 뿐. 사용자 가치는 §2.6 지표가 별도로 담당 — 이 함정을 피하려고 이 문서는 버킷을 분리했다.
- **단일 지표의 단정** — 어떤 지표도 "유일한" 증거가 아니다. 변이 점수·리허설 같은 강한 지표도 하나의 신호로만 읽는다.

## 5. 평가 보고서 템플릿

```markdown
# <프로젝트> 평가 — <날짜>
## 규모        — LOC·파일·커밋·기여자
## 검증 실측   — 실행한 명령과 결과 (추정 표기 금지)
## 지표 표     — 버킷별 수치 + 이전 대비 Δ (N/A는 사유와 함께 명시)
## 가치 판정   — §2.6 버킷 단독 평가 (정합 점수와 합산하지 않음)
## 강점        — 근거가 있는 것만
## 리스크      — 지표→깨짐 시나리오 변환, 영향×확률 순
## 권고        — 순서 있는 3개 이하
```

## 6. 판정 척도

수치를 판정으로 바꿀 때 같은 척도를 쓴다 — 다른 평가자가 같은 수치에 같은 판정을 재현하기 위해서다.

| 판정 | 정의 |
|------|------|
| **강함** | 해당 축이 프로젝트의 경쟁 우위 — 다른 프로젝트가 벤치마크할 수준 |
| **양호** | 요구 수준 충족, 알려진 결함 없음 |
| **주의** | 작동하나 약점이 알려짐 — 감시 또는 계획된 개선 대상 |
| **취약** | 알려진 결함이 방치 — 사고 시 복구 경로가 불명확 |
| **공백** | 측정 불가 — 측정 수단 자체가 없음 (최악은 아니지만 보이지 않는 리스크) |
| **N/A** | 해당 프로젝트 유형에 적용 불가 — 사유 필기 필수 |

판정은 수치가 아니라 **근거 문장**과 함께 적는다: "양호 — 커버리지 70%이고 래칫으로 단조 증가 강제"처럼. 근거 없는 판정은 판정이 아니다.

## 7. 다른 프로젝트에 적용할 때

이 문서는 **체크리스트가 아니라 메뉴 + 해석 프레임**이다. §1~§6은 범용, §8~§9는 이 저장소 전용(측정 소스·실측 사례). 적용 절차:

1. **버킷을 가져가고 지표는 선택** — 전제(테스트 계층·커버리지 도구·배포 산출물·커밋된 생성물)가 없는 지표는 "측정 공백"으로 표기하고 넘긴다. 지표가 없는 것 자체가 평가 결과다.
2. **유형 프로필로 가중치 결정** — §2.8 표에서 해당 유형을 찾아 핵심 버킷과 추가 지표를 확정한다. 표에 없는 유형이면 가장 가까운 것을 변형한다.
3. **도구는 생태계로 치환** — "측정 예시"란의 경로를 해당 언어·플랫폼의 실제 도구로 대응시킨다.
4. **N/A 버킷도 유지** — 생략하면 다음 평가자가 "빠뜨린 것"과 "불필요한 것"을 구분하지 못한다.
5. **§8 위치에 자체 측정 경로를 기록** — "수치가 아니라 재현 명령"을 남겨야 추세 비교가 가능하다.
