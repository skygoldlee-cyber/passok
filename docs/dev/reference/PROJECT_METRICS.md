# 프로젝트 평가지표 — 범용 프레임워크와 측정 규약

> **문서 ID**: DOC-REF-15
> **범위**: platform · 판본: none
> **관련 SPEC ID**: 해당 없음 (평가 방법론 — 측정값의 저장소별 소스는 §6)
> **대상**: 이 저장소(또는 다른 프로젝트)의 상태를 정량 평가하는 사람

## 1. 목적과 원칙

평가지표는 "프로젝트가 건강한가"에 대한 질의응답 도구다. 원칙 세 가지:

1. **스냅샷보다 추세** — 단일 시점 수치보다 변화율(커버리지 증감, 부채 누적 속도)이 신호다.
2. **정합 지표와 가치 지표를 구분** — "문서↔코드 일치" 같은 내부 정합은 부패를 막지만 사용자 가치를 증명하지 않는다. 두 계열을 혼합 평가하면 높은 정합 점수가 낮은 가치를 은폐한다.
3. **측정되는 것은 최적화된다**(Goodhart) — 지표를 게이트로 쓰면 게이트 통과 자체가 목표가 된다. 지표는 진단용이며 목표는 제품이다.

## 2. 지표 체계 — 5개 버킷

### 2.1 규모·생산성 (규모의 무게)

| 지표 | 측정법 | 해석 |
|------|--------|------|
| 소스 LOC / 파일 수 | 언어별 집계 | 절대 수보다 최대 파일 크기·모듈 수 분포가 중요 |
| 테스트 LOC / 소스 LOC 비율 | 테스트 디렉터리 집계 ÷ 소스 | 0.5~1.0이 일반적. 1.0 초과는 테스트 비대 또는 소스 과소 신호 |
| 도구·인프라 LOC 비율 | 도구 디렉터리 ÷ 소스 | 도구가 앱의 30%를 넘으면 인프라 유지비 자체가 리스크 |
| 커밋 속도 | 기간당 커밋 수 | 단일 작성자 초고속 이력은 맥락 손실 리스크의 프록시 |
| 기여자 수 / 버스 팩터 | `git shortlog` | 1이면 지식 보존 인프라(§2.5)가 필수 |

### 2.2 품질·검증 (오류가 잡히는가)

| 지표 | 측정법 | 해석 |
|------|--------|------|
| 테스트 수(계층별) | unit/integration/E2E 분리 집계 | 피라미드 형태인가 — E2E만 많으면 피드백이 느림 |
| 테스트 실통과 | CI 최근 N회 성공률 | 통과 기록이 없는 테스트 수는 장식 |
| 커버리지 | 병합 리포트 (stmts/branch/func/line) | 절대치보다 핵심 경로 커버와 추세. 래칫(단조 증가)이 회귀 방지 |
| 정적 분석 위반 | lint 오류/경고 수, type 오류 | 경고 0 정책이 유지되는지 — `eslint-disable` 주석 수는 규약 우회량 |
| 변이 테스트 점수 | Stryker 등 | 테스트가 실제로 버그를 잡는지의 유일한 직접 지표 |
| 금지 패턴 잔존 | TODO/FIXME, 디버그 코드, 미사용 자산 | 부패 축적량의 직접 측정 |

### 2.3 유지보수성 (변경 비용)

| 지표 | 측정법 | 해석 |
|------|--------|------|
| 최대 파일 크기·순환 복잡도 | 정적 분석 | 큰 파일 하나가 수정의 중심이면 분해 후보 |
| 의존성 개수·신선도 | package.json, out-of-date | 의존이 적을수록 공급망 리스크↓. 고정 버전 여부 |
| 코드↔선언 정합 | 도메인 게이트 통과 여부 | 설정 파일이 실제 동작을 반영하는가 |
| 생성물 신선도 | 빌드 산출물↔원본 diff | 생성물을 커밋하는 저장소는 신선도 게이트가 필수 |

### 2.4 운영·배포 (실제로 사는가)

| 지표 | 측정법 | 해석 |
|------|--------|------|
| 배포 경로 단일성 | 배포 진입점 개수 | 복수 경로 = 가드 우회 가능 |
| 배포 후 스모크 | 자동 검증 존재 여부 | 배포 성공 ≠ 앱 동작 |
| 롤백 경로 | 이전 버전 복원 절차 유무·검증 | 문서에만 있고 실행해본 적 없으면 미검증 |
| 장애 이력·MTTR | 인시던트 기록 | 기록 부재는 무장애가 아니라 미관측일 수 있음 |

### 2.5 지식 보존·온보딩 (맥락이 복원되는가)

| 지표 | 측정법 | 해석 |
|------|--------|------|
| ADR 수·밀도 | 결정당 대안·근거 기재율 | 수보다 "기각된 대안" 기록 유무가 핵심 — 재제안 방지 |
| 런북 커버리지 | 운영 시나리오 대비 문서 비율 | 평시 절차보다 "깨졌을 때" 절차 유무 |
| 문서 신선도 | 문서↔코드 정합 게이트 | stale 문서는 문서가 아니라 함정 |
| **낯선 눈 리허설** | 무컨텍스트 작업 성공률·막힘 수 | 지식 보존의 유일한 실증 지표 — 문서 존재 ≠ 문서 유효 |
| 온보딩 시간 | 신규 기여자의 첫 기여까지 시간 | 리허설로 주기 측정 |

## 3. 평가 프로세스

1. **측정** — §2 지표를 자동 수집 가능한 것부터. 수동 측정은 재현 명령을 함께 기록한다.
2. **해석** — 각 지표에 "정상 범위"가 아니라 "이 프로젝트의 문맥상 의미"를 붙인다 (예: 솔로 프로젝트의 기여자 1은 결함이 아니라 전제).
3. **리스크 변환** — 지표 → "무엇이 깨질 수 있는가" 문장으로. 숫자 자체는 행동을 유도하지 못한다.
4. **우선순위** — 영향×확률로 정렬. 측정이 안 되는 리스크는 리허설·탐색으로 실증한다.
5. **재평가 주기** — 주요 변경 후, 또는 분기 1회. 평가 보고서 자체도 문서로 남겨 추세를 만든다.

## 4. 함정 — 지표 해석에서 자주 틀리는 것

- **테스트 수 = 품질** — 1,271개 통과는 "해당 단언이 깨지지 않음"만 뜻한다. 변이 점수 없이는 단언 밀도 미지수.
- **커버리지 상한 효과** — 70%가 높은지는 제외된 30%의 내용이 정한다. 측정 불가 모듈을 분모에서 뺐는지 확인.
- **문서 수 = 문서화** — stale 문서는 음의 가치. 정합 게이트 없이 문서 수를 세면 부패를 가산한다.
- **게이트 수 = 강함** — 게이트 자체의 유지비와 오탐률을 같이 본다. 오탐이 쌓이면 우회(`--no-verify`)가 관례가 되어 게이트가 무의미해진다.
- **높은 정합 점수 = 높은 품질** — 내부 정합은 자기 일관성일 뿐이다. 사용자 시나리오의 정확성은 별도 지표(E2E·실사용·오류 텔레메트리)가 담당.


## 6. 다른 프로젝트에 적용할 때

이 문서는 **체크리스트가 아니라 메뉴 + 해석 프레임**이다. §1~§5는 범용, §7은 이 저장소 전용(측정 소스·실측 사례). 적용 절차:

1. **버킷을 가져가고 지표는 선택** — 프로젝트에 없는 전제(테스트 계층·커버리지 도구·배포 산출물·커밋된 생성물)가 필요한 지표는 "측정 공백"으로 표기하고 넘긴다. 지표가 없는 것 자체가 평가 결과다.
2. **도구명은 생태계로 치환** — ESLint→린터, Stryker→변이 도구, c8/Vitest→해당 언어 커버리지 체인.
3. **N/A 버킷도 유지** — 배포가 없는 라이브러리는 §2.4를 "해당 없음"으로 기록하고 생략하지 않는다 — 생략하면 다음 평가자가 빠뜨렸는지 불필요가 됐는지 구분이 안 된다.
4. **§7 위치에 자체 측정 경로를 기록** — "수치가 아니라 재현 명령"을 남겨야 추세 비교가 가능하다.
