시험 팩이 계속 추가(`content/exams.json` 23팩)되고 웹툰·아바타·문서 생성기 등 고도화 기능이 쌓이면서, Vanilla ES Modules 접근법의 구조적 한계와 외부 UI 라이브러리 도입 가능성에 대한 검토 요청이 발생했다. 본 문서는 ①Astryx·shadcn/ui의 적합성 판정과 ②현 구조의 실측 한계 진단, ③한계 해소의 단계별 경로를 정리한다.

## 3. Astryx·shadcn/ui 적합성 판정

| | Astryx (Meta, Beta) | shadcn/ui |
|---|---|---|
| 요구사항 | **React 19+** (peer dep), StyleX | **React** + Tailwind CSS (Next/Vite 등) |
| 형태 | 사전 빌드 CSS + typed React 컴포넌트 150+ | 소스 복사·소유 방식 React 컴포넌트 |
| 번들러 | 필수 (npm 패키지 + CSS import) | 필수 (Tailwind 빌드 파이프라인) |

**판정: 둘 다 React 전용 — 현 아키텍처에서 직접 적용 불가.** 충돌 지점:

1. **프레임워크 부재** — `html/views/*.html` 파셜 + 정적 조립 구조에 React 렌더 런타임이 없음
2. **빌드 파이프라인 부재** — 빌드 스크립트(`build:data`·`build:html` 등)는 데이터 번들·HTML 조립뿐. Vite류 번들러 신규 도입 필요
3. **CSS 토큰 이중 관리** — 기존 `--control-h-sm/md/lg`, `--gap-ctl/group/sec` 규약(SPEC §4.8.9)과 외부 디자인 시스템 테마의 중복 발생
4. **PWA 오프라인 전략 재설계** — `sw.js` 프리캐시 목록 + React 번들로 캐시 크기·무결성 관리 부담 증가
5. **재작성 규모** — 뷰 12개 + carework 뷰 ~17개 + 팩 모듈 전부 React 전환 → 사실상 전면 재구축
6. **AI 워크플로 실익 부재** — Astryx의 강점(에이전트 친화 CLI)은 본 리포의 SPEC ID·docs-first·검증 게이트 체계로 이미 상쇄됨

## 4. Vanilla ESM의 실제 한계 진단

팩 수 증가 자체는 현 구조로 감당된다(콘텐츠 팩은 코드와 무관). 진짜 한계는 **기능 복잡도**에서 온다:

1. **컴포넌트 모델 부재** — 문자열 템플릿 + `innerHTML`(443곳) + 수동 DOM 동기화. 문서 편집·대시보드·웹툰 플레이어처럼 상태가 많은 기능에서 상태↔UI 불일치 버그가 **이론적으로** 누적될 수 있음 (현재 표면은 일회성 렌더 중심이라 실측 결함은 미확인)
2. **생태계 격리** — `docx-utils.js`(직접 OOXML 작성), `pdf-registry.js`(2,054줄) 등 성숙 라이브러리 대신 자체 구현 비용이 계속 발생
3. **타입 안전 한계** — JSDoc 수준. 63K LOC에서 리팩터링 안전망이 약함
4. **콜드 로드·SW 관리** — 수백 개 모듈 날것 서빙 + `sw.js` 캐시 목록 수동 관리 (sync 도구로 보완 중이나 구조적 한계)
5. **표준 패턴 부재** — `entity-store`, `data-click` 등 자체 컨벤션은 docs-first로 상쇄되나 신규 기여자·에이전트 학습 비용 존재

## 5. 해소 경로 — 4단계 그래디언트

핵심 통찰: **"빌드 없는 vanilla"을 유지하면서도 컴포넌트 모델은 도입 가능**하다. lit-html, Preact+htm, petite-vue 모두 단일 ESM 파일로 vendor 가능하다.

### A. 무-빌드 유지 + 컴포넌트 모델만 도입 — **벽에 부딪혔을 때의 최소 비용 답안**

- **lit-html**(~6KB) 또는 **petite-vue**(~6KB)를 vendored ESM으로 추가 — `import` 한 줄로 동작, 빌드 불요
- 현재 `ui-utils.js`의 `trainerResultHtml` 같은 마크업 팩토리 패턴을 tagged template으로 자연 진화 가능
- **선행 도입 근거는 약함** — 현재 표면(퀴즈·리더·폼)은 일회성 렌더 + 이벤트 위임으로 충분하며, lit-html은 컴포넌트 모델이 아닌 템플릿 갱신이라 실익은 diff 갱신·이스케이프 기본값 정도. 한 패턴 혼재는 컨벤션 통일성이 강점인 본 리포에서 비용이 더 큼
- **도입 트리거**: 웹툰 플레이어·보이스 동기처럼 재생 상태 + 다중 DOM 반영이 필요한 기능에서 수동 sync가 버그를 낳기 시작할 때 — 그때 이 경로가 가장 저렴한 첫 수
- 비용: 거의 없음 · 잃는 것: 없음 · 무-빌드 철학 유지

### B. Web Components(Lit) 표준화 — 팩 확장 모델과 궁합 최상

- Custom Elements는 웹 표준 → 프레임워크 종속 없음, 빌드 없이 동작
- `<care-calc>`, `<care-roster>` 같은 팩별 엘리먼트로 **DA-13 격리를 더 강하게** 구현 가능
- 공용 UI 키트(버튼/카드/모달) 커스텀 엘리먼트 표준화 → 팩 온보딩 시 마크업 재사용성 상승
- 비용: 테스트 패턴(jsdom shadow DOM) 재정립, 커스텀 엘리먼트 학습 곡선

### C. 빌드 도구만 도입 (Vite) — 프레임워크 없이

- Vite는 framework-agnostic: 현재 ESM 구조 그대로 번들·코드스플릿·minify
- 얻는 것: 콜드 로드 최적화, `vite-plugin-pwa`로 precache 자동화, **TS 점진 전환 경로**, npm 생태계 개방(차트·에디터 등 필요분만)
- 잃는 것: 무-빌드 단순성, `serve.js`/`vercel.json` 재설계, SW 캐시 전략 변경, docs 전면 개정
- **트리거 신호**: "TS로 쓰고 싶다" / "번들 크기가 문제다" / "npm 라이브러리 필요가 계속 발생"이 실제로 확인될 때

### D. 아일랜드(Astro) 또는 전면 React — shadcn/astryx가 정말 필요할 때만

- **Astro**: 정적 출력 유지 + 복잡 섬만 React — astryx/shadcn을 섬 단위로 쓰는 유일한 절충안. 단, 라우팅·빌드 전면 재설계
- **React 전환**: 63K LOC + 30 파셜 + 팩 모듈 재작성 — 현 시점 비용 대비 실익 없음 (§3)

## 6. 권장 로드맵

```
현 상태 → 유지 (전환 근거 없음 — 팩 증가는 콘텐츠 문제라 구조 무관)
트리거  → A: lit-html/petite-vue vendored 도입 — 수동 DOM sync가
           실제 버그를 낳는 기능이 출현하면 그 기능에 한해 최초 대응
성장기  → B: 공용 UI를 Web Components로 표준화, 팩 온보딩 템플릿화
한계점  → C: Vite 도입 (TS 전환·번들 최적화·npm 생태계 필요 확인 시)
필요시  → D: React 섬(Astro) — 전면 재작성은 계속 회피 가능
```

**공용 컴포넌트 CSS 계층 정리**는 별도 프로젝트로 추진할 가치가 낮다 — 토큰 규약(UX-CTL)이 이미 존재해 급한 병목이 아니며, 다른 작업 중 만지는 파일에서 점진 추출이 합리적이다.

**판단 기준**: 전환을 정당화하는 것은 팩 수가 아니라 ①**상태 많은 인터랙티브 기능의 누적으로 수동 DOM 관리가 실제 결함을 유발**하는 신호와 ②**npm 생태계 필요의 반복 발생**이다. 두 신호가 없는 한 현 구조 유지가 정답이며, A~D는 트리거별 대응 카드로 보관한다.

## 7. 현 방식 내 개선 과제 (패러다임 전환 없이 가능)

프레임워크 도입과 무관하게 현 패턴의 연장선에서 가능한 개선을 검토했으나, **조사 결과 핵심 항목 상당수가 이미 구현·게이트화되어 있었다**. 본 절은 실측 기준으로 "이미 완료"와 "잔여 과제"를 구분해 기록한다.

### 7.A 이미 구현됨 (검토 시점 2026-11-28 실측)

### 7.B 잔여 과제 (실제 미구현분) — 항목별 적용 판정 (2026-11-28 실측 보강)

보강 실측: `!important` 396개 중 249개(63%)는 `print.css`(102)+`app-responsive.css`(147)의 인쇄 강제·반응형 오버라이드로 **정당 용도** — 명시도 전쟁 실증은 `reader.css` 56 + `reader-mermaid.css` 52(mermaid 주입 스타일 충돌 추정) 수준. `addEventListener` 412개 중 `click`은 173개뿐이며 `document/window` 리스너 76개는 위임 불가한 정당 직접 바인딩.

**7.B.1 CSS `@layer` 도입 — 명시도 관리 구조화 · 판정: 기회비용 대기열 최상위**

CSS 17파일 457KB·커스텀 프로퍼티 379개인데 `@layer` 사용 0. `@layer base, components, views, exams;` 선언으로 명시도 구조화·`css/exams/`를 `exams` 레이어 격리 시 DA-13 철학과도 일치 — 구조적 실익은 진짜다. 단, 레이어 배정은 캐스케이드 우선순위 자체를 바꿔 **시각 회귀 위험**이 있으므로 visual e2e(`visual.spec`) 전체 실행과 묶은 집중 세션 1회로 처리할 것 — 즉시 적용보다 검증 기회 동반 타이밍.

**7.B.2 `<template>` 태그 패턴 — 판정: 기각으로 하향**

반복 마크업을 파셜 `<template id>` + `cloneNode`로 옮기는 안. 그러나 `html`` 헬퍼(§7.A)가 이미 안전성과 마크업-로직 근접성을 제공하며, `<template>` 방식은 동적 리스트에 장황하고 마크업을 파셜/JS 두 파일로 쪼개 추적 비용을 키운다. 정적 골격이 반복되는 희소 사례 외 실익이 비용을 넘지 않음 — 광범위 적용은 비추천.

**7.B.3 이벤트 바인딩 패턴 통일 — 판정: 유보**

`addEventListener` 412 vs `data-click` 304의 "혼재" 프레이밍은 과장 — lint로 커버 가능한 것은 click 173개뿐이고 document/window 리스너 76개는 정당이다. 리스너 누수의 실증 버그 관측 전까지 규칙 비용 > 실익. 좁은 규칙(뷰 내 요소의 click 직접 바인딩만 탐지)이라도 false positive 부담이 남는다.

**7.B.4 파일 LOC 예산 — 판정: 기각 수준**

`check:cplx` 래칫이 복잡도를 이미 커버하며, 파일 크기만으로는 차단 근거가 약하다(`pdf-registry.js` 2,054줄은 레지스트리 특성상 데이터 집적). 필요해지면 `audit:*` advisory로 추가 가능하나 현 시점 추진 근거 없음.

### 7.C 정리 — 최종 판단: 지금 적용할 항목 없음

XSS 표면 관리·저장소 계약·복잡도 래칫은 이미 게이트로 정착됐고(§7.A), 잔여 4항은 실측 보강 결과 **전부 기회비용 대기열**이다: `@layer`만 시각 회귀 검증 기회와 묶어 실행 가치가 있고, `<template>`는 `html`` 존재로 기각, 이벤트 통일·LOC 예산은 실증 결함 관측 전까지 보류가 정직한 판단이다. 이 리포의 프론트엔드 보완 여지는 초기 추정보다 작다.
