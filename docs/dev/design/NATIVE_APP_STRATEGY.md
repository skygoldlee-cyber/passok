# 네이티브 앱 전환 전략 검토 — PWA 검증 → 네이티브 단계

> **문서 ID**: DOC-DSN-39
> **범위**: platform · 판본: none
> **관련 SPEC ID**: LP-01~10 (프로모션 진입점) · P-01~07 (PWA)
> **성격**: 전략 검토 메모 — 구현 설계가 아닌 의사결정 기록. 네이티브 착수 시 별도 설계 문서 신설

## 1. 배경·요청

"PWA로 초기 사업성이 검증되면 Flutter 기반 네이티브 앱을 개발"한다는 계획에 대한 검토 기록 (2026-10-25).

## 2. 결론

**방향은 타당하나 Flutter 직행보다 TWA → Capacitor → Flutter 순으로 비용을 올리는 것이 합리적.**

- TWA(Play Store)는 코드 재작성 없이 지금 가능 — 검증 단계에서 "스토어 네이티브"를 가장 싸게 얻는 경로
- Flutter는 "웹으로 안 되는 것"이 실데이터로 입증될 때 착수 — 그전엔 이중 유지 비용만 발생

## 3. 리포지토리 기준 Flutter 전환 비용

| 자산 | 재사용 여부 | 비고 |
|---|---|---|
| 도메인 로직 (FSRS·숙달 추적·주간 배분·추천·약점 분석 등 순수 함수 ~20+ 모듈) | **전면 재작성** | JS→Dart 이식 — 제품 핵심 가치이며 가장 큰 비용 |
| 콘텐츠 파이프라인 (MD 파서·build:data·드릴·교재 리더) | 부분 | 파서 재구현 또는 네이티브가 기존 data/ 번들을 웹뷰로 소비 |
| UI/뷰 (~170 src 파일) | 전면 재작성 | Vanilla ES 모듈 → Dart 위젯 변환 불가 |
| 게이트·테스트 체계 (~70 검증 단계) | 재구축 | JS 전용 도구 체인 |
| 사용자 데이터 | 이관 경로 없음 | localStorage → 네이티브 마이그레이션 필요 — Supabase 동기화(현 Pro)가 유일한 다리 |

규모: 수주가 아닌 **수개월의 전면 재작성** + 그 기간 웹 유지 비용 이중 발생.

## 4. 권장 단계

1. **TWA (Trusted Web Activity)** — Play Store에 기존 PWA를 그대로 출시. Digital Asset Links 검증 + 앱 패키지 래핑만 필요 (코드 재작성 0). 스토어 노출·설치 신뢰도를 검증 단계에서 즉시 확보
2. **Capacitor 래핑** — iOS 스토어가 필요해지면 웹 코드를 네이티브 셸로 포장. JS 100% 재사용 + 푸시·네이티브 플러그인 추가 가능
3. **Flutter** — 웹 불가 근거가 데이터로 입증될 때만. 가장 현실적 트리거: iOS PWA의 푸시 알림·백그라운드 제약, 위젯/홈 화면 통합 요구

## 5. 지금 해두면 전환 비용이 줄어드는 것

- **순수 로직의 DOM 격리 유지** — study-tracker·recommendations·fsrs 등이 이미 순수 함수라 Dart 이식이 가장 쉬운 부분. 이 격리를 깨지 않는 것이 최고의 이주 대비
- **스토리지 계층 유지** — backend 교체 가능 구조 유지 (네이티브 어댑터만 갈면 되게)
- **데이터 스키마 버전 관리** — 이후 마이그레이션 도구의 전제 조건
- **Supabase 동기화를 "데이터 이주 경로"로도 기획** — 네이티브 이동 시 사용자 데이터 이동이 이것에 의존

## 6. 재검토 트리거

다음 중 하나 충족 시 Flutter 착수를 재검토:

- 스토어 유입이 총 유입의 상당 비중을 차지하고 웹 전환율이 낮을 때 (TWA 데이터로 측정)
- iOS 푸시/백그라운드 기능 요구가 핵심 유스케이스로 확인될 때
- 웹 성능(대용량 교재 렌더·오프라인 연산) 한계가 사용자 불만으로 나타날 때
