# 임베딩 기반 의미 유사도 — 시맨틱 검색·혼동쌍·유사 문항 설계

> 상위 문서: [SPEC](../SPEC.md) §3.1.5(AN-10), §3.9(TS-08~11), §3.11(DR-05)
> **범위**: platform · 판본: none
> **상태**: 임베딩 인프라 구현됨 (`npm run build:embeddings` → `{dataRoot}/embeddings/` 벡터·이웃 인덱스 번들, `check:embfresh` 신선도 게이트, `src/search/semantic-index.js`) · 의미 소비 표면 일부와 오답 원인 자동 분류(하단 절 — 구 `SEMANTIC_EMBEDDING_DESIGN.md`)는 미구현
> **관련 SPEC ID**: `AN-10`(개념 앵커) · `AN-02`(진단 요약) · `AN-07`(오답 원인 분류) · `AN-09`(주간 리포트) · `TS-08`(역색인) · `TS-09`(인덱스 캐싱) · `TS-10`(서사 검색) · `TS-11`(참조자료 검색) · `DR-05`(취약 진술 리뷰) · `DA-02`(빌드 번들) · `DA-05`(로컬 저장) · `DA-06`(멀티시험) · `DA-08`(피처 플래그) · `PF-02`(온디맨드 로딩) · `SEM-05`(임베딩 신선도)
> **문서 ID**: DOC-DSN-18

## 1. 배경·목적

현재 "의미적 근접성"을 다루는 두 경로가 모두 구조 좌표에 의존한다:

- **취약 개념 클러스터(AN-10)**: 문항·진술의 `conceptId`는 첫 교재 인용의 `§챕터.절` 앵커다. 같은 개념이라도 인용 절이 다르면 서로 다른 버킷으로 분열하고, 반대로 같은 절 안의 무관한 진술은 한 버킷에 섞인다. "구조적으로 다른 위치에 있지만 의미적으로 혼동되는 진술 쌍"은 탐지 자체가 불가능하다.
- **교재 검색(TS-08~09)**: 공백 토큰 + 2-gram 역색인 기반 리터럴 매칭이다. 표현이 조금만 달라져도(동의어, 조사 변형, 영한 혼용) 미스가 발생한다.
- **오답·취약 후속 행동**: 진술을 틀리면 `statement_stats`가 같은 `sid`만 추적한다. "이 진술과 비슷한 다른 진술/문항"을 찾아주는 경로가 없다.

목표는 **정적 배포·오프라인 PWA 제약을 깨지 않으면서** 콘텐츠 간 의미 유사도를 제공하는 것이다. 핵심 결정: **임베딩 계산은 빌드 파이프라인에서만 수행하고, 앱에는 벡터 자산과 코사인 유사도 코드만 배포한다.** 브라우저에는 모델이 없다 — 추론 비용·모델 자산·네트워크 의존을 모두 빌드타임으로 이동시키는 것이 이 설계의 전제다.

## 2. 비목표

- **자유 텍스트 질의의 시맨틱 검색** — 쿼리 문자열을 벡터화하려면 런타임 모델 또는 원격 API가 필요하다. v1 범위는 아이템→아이템 유사도뿐이며, 쿼리 임베딩 경로는 §8의 트레이드오프를 검토 후 별도 결정한다.
- **지식 추적(DKT/AKT)·추천 강화학습** — 별개 과제.
- **생성형 콘텐츠(오답 해설, 유사 문항 생성)** — 임베딩은 기존 콘텐츠 검색·연결에만 쓴다. 새 텍스트를 만들지 않는다.
- **실시간/온라인 기능** — 네트워크 없이 동작해야 한다. 원격 임베딩 API는 선택적 BYOK 경로(§8-2)로만 존재한다.

## 3. 모델·차원 선정

| 후보 | 차원 | 파라미터 | 라이선스 | 한국어 | 비고 |
|---|---|---|---|---|---|
| `intfloat/multilingual-e5-small` | 384 | ~118M | Apache-2.0 | ✅ 다국어(한국어 포함) | `"query:"`/`"passage:"` 접두사 필요. **1차 추천** |
| `paraphrase-multilingual-MiniLM-L12-v2` | 384 | ~118M | Apache-2.0 | ✅ | 접두사 불필요. e5보다 한국어 STS 성능 낮음 |
| `snunlp/KR-SBERT-V40K-klueNLI-augSTS` | 768 | ~111M | CC-BY-SA-4.0 | ✅ 특화 | 차원 2배 → 벡터 자산 2배. 품질 게이트 미달 시 대안 |
| `jhgan/ko-sroberta-multitask` | 768 | ~111M | Apache-2.0 | ✅ 특화 | 동일한 차원 비용 문제 |

**선정 근거**: 벡터 자산 크기는 차원에 정비례하므로 384d 모델이 768d 대비 번들을 절반으로 만든다. 임베딩 대상은 단문(진술 평균 ~30자)·전문 용어 텍스트라 모델 간 체감 차이가 벤치마크 평균보다 작을 가능성이 높으므로, **e5-small을 기본으로 하고 §9의 평가 게이트(recall@k)에서 기준 미달 시에만 768d 한국어 모델로 격상**한다. 모델명·리비전·파라미터는 매니페스트에 기록해 교체 시 재빌드만으로 전환되게 한다.

**차원 축소 옵션**: 384d를 유지하는 것이 기본이다. 번들 크기가 예산(§6-3)을 초과하면 빌드타임 PCA(또는 e5 계열의 head-truncation)로 128d까지 축소를 검토한다 — 축소 여부·기법·분산 설명력도 매니페스트에 기록한다.

**재현성**: 생성 도구는 `tools/build/build_embeddings.js` — 동일 모델의 ONNX export(`Xenova/multilingual-e5-small`, fp32)를 `@huggingface/transformers`로 인코딩한다. 모델은 커밋 SHA로 핀한다(`tools/lib/emb_math.js`의 `EMB_MODEL_REVISION` — revision 미지정 요청은 HF main 최신을 따라가 출력 drift를 허용하므로). 매니페스트 `revision`은 `<repo>@<sha>`로 기록된다. fp32 ONNX 출력은 원본 PyTorch 산출물과 int8 양자화 후 완전 일치함이 `tools/check/check_emb_parity.js`로 검증됐다(벡터 cos 1.00000·이웃 일치 95.7%). 동일 입력이면 동일 벡터가 재생산되어야 하며, 매니페스트의 `sourceHash`(입력 텍스트 집합 해시)가 신선도 게이트의 비교 기준이 된다(§7-3). Python 레퍼런스 구현은 `ref-pipeline/embeddings/build_embeddings.py`에 보존한다.

## 4. 임베딩 대상·ID 체계

| 엔티티 | ID | 텍스트 소스 | 규모(cosmetic 기준) |
|---|---|---|---|
| `statement` | `sid` (DR-03, `{subject}\|{section}\|{kind}\|{key}`) | O/X·ㄱㄴㄷ 진술 원문 | ~5,000 (O/X 3,703 + combo 진술) |
| `question` | `qid` (문제은행 `### Q` id) | 발문 + 정답 텍스트 | ~1,000 |
| `card` | 카드 `stableId` | term + definition | ~1,123 |
| `chunk` | `{file}#L{line}` 교재 청크 id | `##`/`###` 절 단위 분할 본문 (~512자 상한) | ~3,000~4,000 |

- **`statement`가 1차 대상**이다 — 취약 진술 리뷰(DR-05)·혼동쌍의 직접 소비자.
- `chunk`는 교재 검색 확장(§8)과 "근거로 돌아가기" 딥링크를 위한 것으로, 검색 인덱스(TS-08)가 쓰는 row 좌표(`file`+`line`)와 동일한 좌표계를 사용해 결과를 그대로 교재 뷰어 링크로 변환한다.
- 텍스트 전처리는 기존 `normalize()`(검색용 소문자·공백 정규화)와 분리한다 — 임베딩 입력은 **원문 유지**(조사·어미가 의미 신호). 모델 입력 전 최소 정리(연속 공백 압축, 마크다운 기호 제거)만 적용한다.
- `sid`는 내용 해시 기반이므로 진술 문구 편집 시 id가 바뀌고 벡터도 재계산된다 — 이는 `statement_stats`의 동일 라이프사이클과 일치해 별도 이관이 필요 없다.
- 사용자 생성 데이터(오답 이력, 태그)는 임베딩 입력에 포함하지 않는다 — 벡터는 순수 콘텐츠 자산이다.

## 5. 번들 형식·매니페스트

기존 데이터 자산 규약(DA-02: 해시드 JS 번들 + `<script>` 로드, file:// 호환)을 그대로 따른다.

```
{dataRoot}/embeddings/
  manifest.js              → window.EMB_MANIFEST
  vectors_stmt_<examKey>.js → window.EMB_VEC_stmt_<examKey>   (과목별 분할)
  vectors_questions.js      → window.EMB_VEC_questions
  vectors_cards.js          → window.EMB_VEC_cards
  vectors_chunks_<subjectKey>.js → window.EMB_VEC_chunks_<subjectKey>
  neighbors.js              → window.EMB_NEIGHBORS            (선택 — §5-2)
```

### 5.1 벡터 직렬화 — int8 대칭 양자화 + base64

```js
window.EMB_VEC_stmt_subject4 = {
  model: "intfloat/multilingual-e5-small",
  revision: "e4ce9877…",
  dim: 384,
  quant: "int8",          // per-vector symmetric: b = round(v / max|v| * 127)
  ids: ["s4|…|p|abc…", …],
  scales: [0.0123, …],    // float16 → JSON 근사값, 복원 시 v = b * scale
  vectors: "<base64>"     // Int8Array(ids.length × dim) 직렬화
};
```

- **왜 base64 JS인가**: `file://` 실행 경로는 `fetch`가 차단되어 모든 데이터 자산이 `<script>` 주입(`DataLoader._loadScript`)으로 로드된다. `.bin` 분리는 http 전용 경로를 추가로 만들어야 하므로 v1에서는 규약 준수를 우선한다.
- **크기**: 항목당 `dim`B(int8) ×4/3(base64) + id/scale ≈ **560B**(384d 기준). 전체 ~10k 항목 ≈ 5~6MB → 타입·과목 분할 시 최대 단일 번들 ≈ 1~1.5MB (기존 최대 번들 `ox_subject4.js` 1.3MB와 동급).
- **정확도 비용**: int8 대칭 양자화의 코사인 유사도 오차는 통상 <0.5%p — top-K 순위에 무영향 수준. 빌드 시 왕복 오차를 계측해 리포트한다.
- **역양자화 정책**: 로드 시 복원·L2 정규화해 `Float32Array`로 메모리 캐시(항목당 1.5KB — 4k 항목 ≈ 6MB 메모리, 모바일 허용 범위). 코사인은 복원 벡터의 내적으로 계산한다.

### 5.2 이웃 인덱스 (선택적 프리컴퓨트)

모든 소비자가 전체 벡터를 필요로 하지는 않는다. "유사 문항 top-5"는 빌드타임에 미리 계산해 두면 벡터 로드 없이도 제공된다:

```js
window.EMB_NEIGHBORS = {
  dim: 384, k: 8,
  adj: { "<sid>": [["<sid2>",0.91],["<sid3>",0.87],…], "<qid>": […], … }
};
```

- 항목당 8개 × ~30B ≈ 240B → 10k 항목 ≈ 2.5MB. **벡터 번들 없이 이 파일 하나만으로 유사 문항·유사 진술 UI가 동작**하는 저비용 경로다.
- §6의 소비 지점 중 "고정 top-K만 필요한 곳"(유사 진술 표시, 유사 문항 추천)은 이웃 인덱스를 우선 사용하고, 임의 유사도 계산이 필요한 곳(DOC-DSN-19 센트로이드, 임계값 재탐색)만 벡터를 로드한다 — 로딩 비용을 기능별로 분리하는 이중 구조.

## 6. 런타임 모듈·소비 지점

### 6.1 `src/search/semantic-index.js` (제안, 신규 플랫폼 모듈)

```ts
await SemanticIndex.ensureNeighbors();                    // EMB_NEIGHBORS 지연 로드
SemanticIndex.similar(id, {k?, minSim?, type?, subject?}) // 이웃 인덱스 조회 → [{id,score}]
await SemanticIndex.ensureVectors(type, subject?);        // EMB_VEC_* 지연 로드
SemanticIndex.cosine(idOrVecA, idOrVecB)                  // 임의 쌍 유사도 (벡터 필요)
SemanticIndex.topK(queryVec, {type?, subject?, k})        // 전수 스캔 (벡터 필요)
```

- 로딩은 `DataLoader._loadScript` 패턴 재사용(중복 로드 방지·재시도 포함).
- 전수 스캔 비용: 과목당 최대 ~4k 항목 × 384d ≈ 1.5M 곱셈 — 스칼라 루프로 <10ms, ANN 인덱스 불요.
- **피처 게이트**: `features.semantic`(신규, exams.json 선언 → `check:featflags` 대상). 미선언·번들 부재·로드 실패 시 각 호출 지점은 조용히 숨긴다(점진적 향상 — 기능 없어도 앱 정상).
- `@spec` 태그: 신규 SPEC ID 등록 필요(§11).

### 6.2 소비 지점

| 지점 | 입력 | 출력 | 필요 자산 |
|---|---|---|---|
| 취약 진술 리뷰(DR-05) | 오판 `sid` | "유사 진술" N개 — 다른 §앵커의 의미近 진술까지 노출 | neighbors |
| 오답 후속 추천 (퀴즈·모의고사 리뷰) | 틀린 `qid` | "비슷한 문항" top-k — 미숙지 문항 우선 정렬 | neighbors |
| 혼동쌍 발견(맞춤학습) | `statement_stats`에서 교차 오판 관측된 진술 쌍 | 후보 = `cos ≥ τ` ∧ `cid` 상이 ∧ 양쪽 판정 이력 존재 → 관측된 교차 오판률로 순위 | neighbors(후보) + 사용자 통계(순위) |
| 교재 검색 확장 | 검색 결과 `chunk` | 결과 행에 "관련 내용" 확장 — 선택 chunk의 이웃 표시 | neighbors |
| §앵커 클러스터 보완(AN-10) | `cid` 그룹 | `cos ≥ τ` 쌍을 엣지로 병합/분할 후보 제안 — 구조 앵커는 유지, 의미 링크를 보조로 추가 | vectors 또는 neighbors |

- **혼동쌍의 순위는 사용자 데이터가 정한다**: 임베딩은 "의미적으로 가까운 후보"만 제공하고, 실제 혼동(번갈아 틀리는 패턴)은 `statement_stats`의 판정 이력에서 계산한다 — 콘텐츠 유사도와 사용자 혼동 신호의 책임 분리.
- 추천 노출 상한·빈도 제한은 `recommendations.js`의 기존 패턴(우선순위·스냅샷)에 맞춰 결정한다 — 본 설계는 유사도 원천만 제공.

## 7. 파이프라인·빌드 통합

### 7.1 생성 스크립트 (제안)

- `tools/build/build_embeddings.js` — 생성 스크립트(Node — Python 레퍼런스 `ref-pipeline/embeddings/build_embeddings.py`의 포팅, ONNX fp32 인코딩). 입력: `build:data` 산출물(드릴 번들의 진술·문항) → 출력: §5의 번들 + `manifest.js`.
- npm 스크립트 `build:embeddings` — `build:data`와 독립 실행. 임베딩 재생성은 콘텐츠 변경 시에만 필요하며, CPU에서 ~10k 항목 ≈ 수 분(모델 다운로드 ~470MB는 최초 1회).
- 대형 모델 다운로드·전쌍방 유사도 연산은 무거우므로 **기본 빌드 체인과 분리**한다.

### 7.2 빌드 체인 위치

`build:data` 산출물이 입력이므로 임베딩 빌드는 그 이후에 실행한다. **필수 체인에 포함하지 않는다** — `check:all`이 매 실행마다 모델 다운로드·전쌍방 유사도 연산을 수행하는 것을 막기 위함이다. 대신:

- `manifest.js.sourceHash` = 임베딩 입력(대상 텍스트 집합)의 결정적 해시.
- 신선도 검증은 벡터 재계산 없이 가능: **입력 해시만 다시 계산해 매니페스트와 비교**(해시 입력 스냅샷도 함께 커밋). `check:datafresh` 계열에 `check:embfresh`(제안) 단계를 추가해 "콘텐츠는 바뀌었는데 임베딩이 구형"을 게이트한다. 재계산이 필요할 때만 `build:embeddings`를 수동 실행한다.

### 7.3 서비스워커·자산 정책

- `SHELL_ASSETS`/`DATA_ASSETS` 프리캐시 **비대상** — 설치 크기 비대화 방지(`check:perf` 영향 없음). 런타임 cacheFirst + `warmPracticeFeatures` 유휴 예열로 오프라인 진입을 보장하는 기존 도메인 모듈 패턴을 따른다.
- 최초 오프라인 진입 시 미캐시면 기능 비노출 — `DATA_ASSETS` 승격은 사용 지표 확인 후 결정.

## 8. 자유 텍스트 질의 — 트레이드오프 (v2 결정 보류)

아이템→아이템만으로는 "사용자가 직접 친 질의"의 시맨틱 검색이 불가하다 — 쿼리도 벡터화해야 한다. 경로 비교:

| 경로 | 추가 비용 | 오프라인 | 비고 |
|---|---|---|---|
| A. 쿼리 앵커 — 질의어를 미리 계산된 항목/용어 집합에 스냅(기존 검색 결과 상위 항목의 벡터를 프록시로 사용) | 0 | ✅ | "결과가 나온 항목 기준 관련 항목" — 완전 자유 질의는 아님. **v1.5로 채택 가능** |

**권장 순서**: A(비용 0, 대부분의 실용 효과) → 실사용 지표로 B 필요성 검증 → C는 BYOK 수요 있을 때만. v1에서는 A의 "결과→관련 항목 확장"까지만 범위에 넣는다.

## 9. 품질 검증

- **수치 검증(빌드 시 자동)**: ids 중복 0, 차원 일치, NaN/Inf 0, ‖v‖≈1(양자화 전), 왕복 복원 코사인 오차 보고.

## 오답 원인 자동 분류 설계 — 임베딩 센트로이드 기반 추정기

> 상위 문서: [SPEC](../SPEC.md) §3.1.5(AN-07, AN-02, AN-09)
> **범위**: platform · 판본: none
> **상태**: 설계 검토 (미구현 — 본 문서의 경로·API는 제안이며 아직 존재하지 않는다)
> **관련 SPEC ID**: `AN-07`(오답 원인 분류) · `AN-02`(진단 요약) · `AN-09`(주간 리포트) · `DA-05`(로컬 저장) · `DA-08`(피처 플래그)
> **선행 의존**: DOC-DSN-18 (임베딩 벡터 번들 — 본 설계의 분류 입력)
> 원본 문서: `WRONG_CAUSE_CLASSIFIER_DESIGN.md` — 구 DOC-DSN-19 (2026-10-17 본 문서로 통합)

### 1. 배경·목적

`estimateUntaggedCauses`(src/study/analysis-engine.js)는 사용자가 원인을 태그하지 않은 오답에 정규식 기반으로 원인을 귀속한다:

1. manifest `wrongCauses[].autoPattern` 정규식 히트 → 선언된 확장 키
2. 정답이 수치 → `numeric`(선언 시) 또는 `calc`
3. 발문이 부정형("아닌/틀린/옳지 않은 것") → `concept`
4. 나머지 → `memorize`

한계가 구조적이다 — **문항의 "형식"으로 원인을 추정하지 사용자가 왜 틀렸는지를 보지 않는다**:

- 부정형 문항을 암기 부족으로 틀려도 무조건 `concept`으로 귀속 (규칙 3이 무조건 발동).
- 계산 문항인데 상수·공식 자체를 몰라 틀려도 `calc`로 귀속 — "암기해야 할 수치를 몰랐다"와 "계산 절차를 틀렸다"를 구분 못 함.
- 선택한 오답 선지·인용 근거 텍스트는 입력에 없다 — 같은 문항이라도 "비슷한 수치를 골랐는가, 무관한 개념을 골랐는가"가 원인의 핵심 단서인데 미사용.

사용자 수동 태그(`wrongCauses`)는 정확하지만 태깅률이 낮으면 오답 패턴 카드(AN-02)·주간 리포트(AN-09)가 추정값에 크게 의존한다.

**목표**: 미태깅 오답에 대해 규칙보다 정확한 추정 원인을 **확신도와 함께 제안**한다. 사용자 태그는 항상 우선(authoritative)이며, 본 기능은 추정 품질을 올리는 보조다.

### 2. 비목표

- **사용자 확인 없는 자동 태깅 확정** — 분류 결과는 "추정"으로만 표시한다. `wrongCauses` 기록은 사용자 행위로만 생성된다.
- **오답의 교육적 해설 생성** — 원인 라벨만 분류하고 해설은 만들지 않는다.
- **크로스유저 지도학습** — 단일 사용자 라벨로만 동작한다(데이터 규모상 딥러닝 미세조정 불가 — §3).
- **실시간 트랜스포머 인퍼런스** — 모델 자산을 앱에 싣지 않는다.

### 3. 접근 비교 — 데이터 규모에 맞는 방법 선정

| 접근 | 필요 라벨 | 자산 비용 | 정확도 기대 | 판단 |
|---|---|---|---|---|
| A. 규칙 개선 (autoPattern 확장) | 0 | 0 | 현행 유지 — 형식 휴리스틱 한계 동일 | 폴백으로 유지 |
| B. **임베딩 센트로이드 kNN** — 태깅된 오답의 벡터를 원인별로 평균해 미태깅 오답을 최근접 원인에 배정 | 수십~수백 건 (사용자 태그가 곧 라벨) | 모델 0 — D18 벡터 재사용 | 유사 오답은 유사 원인 경향 — 소량 라벨에서 가장 강건 | **Phase 1 채택** |
| C. 소형 트랜스포머 fine-tune (KoELECTRA-small 등) + ONNX | 원인당 ≥수백 건 + 평가셋 | 모델 수십 MB + 런타임 | 라벨 부족 시 과적합 — 단일 사용자는 한계 명확 | 라벨 임계량 도달 시 재평가 |
| D. LLM 분류 (BYOK 원격) | 0 (few-shot) | 0 | 높지만 네트워크·키·프라이버시·지연 비용 | 선택 경로로만 보류 |

**B를 채택하는 근거**: 단일 사용자의 누적 태그는 수십~수백 건 스케일이므로 지도학습보다 최근접 이웃 계열이 맞고, D18에서 이미 모든 문항·진술의 벡터가 번들로 존재해 **추가 자산·모델 없이 순수 계산으로 구현**된다. 센트로이드는 사용자 본인의 태그로만 구성되므로 개인화도 자연스럽다.

**솔직한 한계 명시**: 센트로이드는 "내가 비슷한 문항에서 이 원인으로 태그했다"의 일반화다. 태그 0건이면 작동하지 않고, 원인 간 의미 차이가 미세한 경우(memorize↔concept) 분리력이 낮을 수 있다 — 그래서 §5의 확신도 게이트와 §6의 기저선 비교가 필수다.

### 4. 입력·분류 체계

#### 4.1 분류 입력 피처

오답 이벤트당 다음을 결합해 임베딩 대상 텍스트를 구성한다:

```
[stem] 발문 + [chosen] 선택한 오답 선지 + [correct] 정답 + [citation] 인용 근거 구절
```

- **`chosen`이 핵심 추가 신호**다 — 같은 문항이라도 어떤 오답을 골랐는지가 원인을 가른다(비슷한 수치 선택 → 수치 혼동; 무관 개념 선택 → 개념 오해). 현행 규칙은 stem만 본다.
- `chosen`이 없는 형식(단답형)은 stem+정답만.
- D18의 `question` 벡터는 stem+정답만이므로, `chosen`까지 반영된 임베딩은 빌드 산출물에 없다. **v1은 D18 문항 벡터(stem+answer)를 그대로 쓰고**, 선지 포함 임베딩은 D18 파이프라인 확장(선지별 벡터 `vectors_distractors`)으로 단계 2에서 추가한다 — 의존성 최소화 우선.

#### 4.2 분류 체계 = 기존 taxonomy 재사용

원인 키 집합은 `getWrongCauseTaxonomy()`(AN-07)를 그대로 따른다 — 기본 3종(memorize/concept/calc) + manifest `analysis.wrongCauses` 확장 키. 시험별 taxonomy 추가는 별도 작업 없이 자동 호환되며, 새 키의 센트로이드도 사용자가 태그를 쌓으면 자연스럽게 형성된다.

### 5. 추정 절차·확신도

```
1. 사용자가 태그한 오답 집합 T = { item → cause }
2. 원인별 센트로이드: C[c] = normalize( mean( v(item) for item in T where cause=c ) )
   — D18 벡터 로드 후 평균, 수십 건 기준 ms 단위. 태그 변경 시점에만 재계산해 캐시.
3. 미태깅 오답 i에 대해: s_c = cosine(v(i), C[c]) for all c
4. best = argmax s_c, margin = s_best − s_second
5. 추정 채택 조건: |T| ≥ MIN_LABELS(기본 20) ∧ margin ≥ τ_margin(기본 0.05)
   ∧ s_best ≥ τ_sim(기본 0.5)
6. 채택 → { cause: best, confidence, suggested:true } / 미달 → 기존 규칙 추정 경로 유지
```

- **margin 게이트**: 두 원인이 근접하면 "분류기가 구분 못 함"으로 판단해 제안하지 않는다 — 잘못된 확신보다 침묵이 낫다(오답 원인은 학습 행동 권고로 이어지므로).
- **라벨 최소량**: `MIN_LABELS` 미만이면 센트로이드 자체를 만들지 않고 규칙 폴백만 — 콜드스타트에서 성능 악화를 막는다.
- 임계값(τ_margin·τ_sim·MIN_LABELS)은 `manifest.analysis.causeClassifier` 선언으로 시험별 조정 가능하게 하되, 미선언 시 위 기본값. 매직 넘버는 `src/config/` 규약대로 상수화.

#### 5.1 제안 UI 연동

- 오답 원인 선택 UI에서 "추정: {라벨}"을 **기본 선택이 아닌 제안 칩**으로 표시 — 사용자가 탭하면 확정, 무시하면 미태깅 유지. 수락/거부를 계수해 §6의 수용률 지표로 사용한다.
- 오답 패턴 카드·주간 리포트의 분포에는 기존처럼 "추정" 표기를 유지하고, 센트로이드 추정분도 동일하게 추정 취급한다(태그와 구분 표기 — AN-07의 counts는 추정치로 이미 표기됨).

### 6. 평가

- **오프라인 검증(빌드/개발 단계)**: 사용자 태그 이력에 leave-one-out — 태그 1건을 숨기고 나머지로 센트로이드 구성 → 숨긴 태그 재현율 vs 규칙 기저선 재현율 비교. **목표: top-1 일치율 ≥ 규칙 기저선 +20%p**, 미달 시 기능을 활성화하지 않는다(롤아웃 게이트).
- **운영 지표(앱 내)**: 제안 수용률(추정 제안 → 사용자 수락 비율)을 카운터로 집계해 AN-09 주간 리포트에 포함. 수용률 <60%이면 τ 상향 또는 표시 빈도 하향.
- **회귀 방지**: 규칙 추정은 항상 계산해 두고 센트로이드 추정만 덮어쓰는 구조 — 센트로이드 경로 버그 시 규칙 결과로 자동 퇴행 가능하게 이중화한다.

### 7. 저장·프라이버시

- **신규 저장 키(제안)**: `wcclf:<examId>:centroids` — 원인별 센트로이드 벡터 캐시(태그 해시로 무효화). `storage.js` 추상화 경유·`<examId>:` 스코프 규약 준수. 백업/동기 포함 여부: **포함** — 사용자 디바이스별 재계산 가능하지만 이동 시 콜드스타트 방지 가치가 있고, 벡터 자체는 원문 비가역이라 프라이버시 민감도 낮음. 단, 사용자 태그 원본(`wrongCauses`)은 기존 정책 그대로.
- 외부 전송 없음 — 모든 계산 온디바이스. D(BYOK LLM) 경로는 채택 시 CSP·키 계약을 FO-BYOK 패턴으로 별도 설계.
- 추정 결과가 `wrongCauses`에 쓰이지 않으므로 저장 데이터 스키마 변경 없음 — 표시 계층만.
