(cid:49684) 데이터베이스 보안 개념
데이터베이스(DB: database)는 조직에 필요한 정보로서 데이터베이스 관리 시스템(DBMS)에 의
해 관리되며 접속하여 SQL을 이용하여 질의어를 통해서만 원하는 정보에 정상적으로 접근한다.
데이터베이스 보안은 데이터베이스에 저장되어 있는 데이터에 대한 인가되지 않은 접근, 의도
적인 데이터의 변경이나 파괴 및 데이터의 일관성을 저해하는 우발적인 사고 등으로부터 데이
터 혹은 데이터베이스를 보호하는 것을 말한다.
데이터베이스 보안은 정보보호의 목표인 기밀성, 무결성, 가용성의 3요소를 가장 잘 유지해야
하는 분야이다.

| DBMS(database management system) |
| --- |
| 데이터베이스와 관련된 정보와 환경 등을 관리하는 시스템을 총칭하여 말한다. 관계형 DBMS로 Oracle,MS SQL Server, MySQL, Tmax, Postgre 등이 사용되고 있다. |

| SQL(structured query language) |
| --- |
| SQL은 관계형 데이터베이스 관리 시스템(RDBMS)의 데이터를 관리하기 위해 설계된 프로그래밍 언어이다.관계형 데이터베이스 관리 시스템에서 자료의 관리와 검색, 데이터베이스 스키마 생성과 수정, 데이터베이스객체 접근 조정 관리 등을 위해 만들어졌다. 현재 많은 수의 데이터베이스 관련 프로그램들이 SQL을 표준으로 채택하여 사용하고 있다. |

(cid:49685) 데이터베이스 보안 목적
데이터베이스 보안 목적은 데이터베이스에 저장된 데이터의 노출, 변조 및 파괴, 훼손, 지체 및
재난 등의 위협으로부터 보호하여 기밀성, 무결성, 가용성 등을 확보하는 것이다. 즉 데이터가
생성되어 처리되고 유통 과정을 거쳐 마지막으로 소멸 또는 폐기되기까지 생명주기 전반에 걸
쳐 기밀성, 무결성, 가용성 등이 확보되어야 한다.

[그림 1-1] 데이터베이스 보안 목적
1. 기밀성(confidentiality)
데이터에 선별적인 접근 체계를 만들어서 인가가 안 된 개인이나 시스템에 의한 접근과 이
에 따른 정보 공개·노출을 막는 것이 기밀성 유지이다. 기밀성은 데이터베이스 내에 중요한
개인정보를 저장하고 있는 사람들의 사생활을 유지하는 데 필요한 최소한의 필수 조건이며
접근제어와 암호화는 기밀성 유지를 위한 대표적인 방법이다.
2. 무결성(integrity)
데이터 무결성은 정당한 방법에 의하지 않고는 데이터가 변경될 수 없는 것을 말하며, 데이
터의 정확성 및 완전성을 보장하고 그 내용이 고의적이거나 악의로 변경되거나 훼손 또는
파괴되지 않았음을 보장하는 것이다.
3. 가용성(availability)
데이터 가용성이란 사용자가 업무 서비스를 필요로 할 때 그 서비스의 연속성을 보장하는
것을 말한다. 이것은 컴퓨팅 시스템이 정확하게 정보를 저장하고 처리하여, 보안 통제가 그
것을 보호하며 해당 정보에 접근하는 데 사용되는 통신 채널이 정확하게 구축되어야 함을
의미한다.
(cid:49686) 데이터베이스 보안요구사항
데이터베이스 보안요구사항은 저장된 데이터에 대한 보안을 위한 사용자의 요구를 수집하고 명
세화하는 작업이다. 데이터베이스 보안요구사항을 종합적으로 검토하고 확인함으로써 요건에
맞는 데이터베이스 시스템을 개발하여 사용자의 만족도를 높이는 것이다.
1. 권한을 부여받은 사용자만 접근 허용
데이터베이스를 부적절한 접근으로부터 보호하기 위해서는 승인된 사용자에게만 접근 권한
을 부여하고 사용자 혹은 응용 시스템의 접근 요청은 DBMS에 의하여 관리되어야 한다.
즉, 정당하게 권한을 부여받은 사용자에게만 데이터베이스 접근을 허용하는 것이다.
2. 추론 방지
추론은 보통의 일반적인 데이터로부터 기밀 정보를 획득할 수 있는 가능성을 의미한다. 추
론 문제는 사용자가 통계에서 얻은 데이터값으로부터 별도의 데이터 항목에 대한 정보를
추적하지 못하도록 하여야 하는 통계 데이터베이스에 많은 영향을 미친다.
3. 데이터베이스의 무결성 보장
데이터의 내용을 수정할 수 있는 인가되지 않은 접근, 저장 데이터를 손상시킬 수 있는 시
스템의 오류, 고장 등으로부터 데이터베이스를 보호하여야 한다. 이러한 유형의 보호는 적
절한 시스템 통제, 다양한 백업 및 복구 절차, 임시적인 보안 절차 등을 통하여 DBMS가
수행한다.
4. 데이터의 논리적 일관성 보장
데이터베이스에서 트랜잭션의 병행 처리 수행 동안에 데이터베이스 내의 데이터에 대한 논
리적 일관성을 보장하여야 한다. 이러한 요구사항은 DBMS의 병행 수행 관리자에 의하여
보장된다. 병행 수행 관리자는 트랜잭션의 직렬성을 보장한다.
5. 감사 기능
다양한 응용 처리에서 데이터베이스에 대한 모든 접근의 감사 기록을 생성하여야 한다. 데
이터에 대한 분류를 통해 중요 정보에 대해 감사 기록을 유지하여 중요 데이터에 대한 비
인가 또는 비정상적 접근을 효과적으로 기록하고 감지하여야 한다.
감사 기록은 데이터베이스의 무결성을 유지하는 데 도움을 주며, 데이터베이스 접근에 대한
후속적인 분석을 가능하게 한다.
6. 사용자 인증
DBMS는 엄격한 사용자 인증을 필요로 한다. DBMS의 사용자 인증은 운영체제에서 수행하
는 사용자 인증보다 더욱 엄격하여야 한다. 전형적으로 DBMS는 운영체제상의 응용프로그
램으로써 실행된다. 이는 운영체제와 DBMS 사이에 신뢰할 수 있는 경로가 없음을 의미한
다. DBMS는 사용자 인증을 포함한 각종 데이터를 운영체제로부터 수신할 때 신뢰할 수 있
는지의 여부를 점검하여야 한다. 따라서 DBMS는 반드시 별도의 사용자 인증 절차를 보유
하여야 한다.
7. 제한
제한(confinement)은 시스템 프로그램 간의 바람직하지 못한 정보 전송을 방지하는 것이
다. 이러한 정보 전송은 은닉 채널을 통하여 발생한다. 은닉 채널은 시스템 주체(프로세스)
간의 통신에 사용할 목적이 아닌 시스템 자원을 사용하여 이루어지는 통신 채널이다.
8. DB 암호화
DB 암호화는 DBMS에 저장된 중요 데이터를 인가되지 않은 사용자에게 평문(plan text)으
로 보여 줄 수 없도록 암호화(encryption)해서 저장하는 것으로 보안을 강화하는 것을 말
한다. <표 1-1>과 같이 DB 암호화 방식은 다양한 방식으로 구현할 수 있다.
<표 1-1> DB 암호화 방식
DB 암호화 내용
- 암복호화 모듈이 API 형태로 칼럼의 평문을 암호화하는 방식
- 암복호화 속도가 빠르고, DBMS 성능에 영향이 없음
API 방식
- DB 서버와 응용시스템 간의 전송 구간에도 암호화된 데이터 전송
- 응용시스템 소스코드 수정을 필요로 함
- 암복호화 모듈이 DBMS에 설치되고 dBMS에서 암복호화 모듈 호출 방식
- DBMS내 Plug-In 형태로 모듈을 적용하여 암복호화 수행
Plug-In 방식
- 암복호화 양에 따라 DBMS 성능 저하 발생

수행 순서
(cid:49684) 정의된 보안요구사항에 따라 데이터베이스 사용 용도를 파악하고 요구사항을 분석한다.
1. 데이터베이스 사용 용도를 분석한다.
데이터베이스의 설계 이전에 가장 먼저 파악하여야 하는 작업이 사용하는 데이터베이스의
사용 용도를 분석하는 일이다. 어떤 업무인지, 어떤 분야에서 사용하는지, 어떤 사용자들이
주로 사용하는지 여부 등을 분석한다.
2. 데이터베이스 보안 설계 목적 및 필요성을 분석한다.
(1) 데이터베이스 보안 목적을 분석한다.
데이터베이스 보안의 목적은 데이터베이스에 저장되어 있는 데이터에 대한 부적절한 접
근이나 의도적인 데이터의 수정, 혹은 삭제 및 데이터의 일관성을 방해하는 사고 등으로
부터 데이터 또는 데이터베이스를 보호하는 것임을 숙지하고 분석한다.
(2) 데이터베이스 보안 필요성을 분석한다.
서버에서 처리되고 저장되는 정보는 신속한 업무 처리와 함께 적절한 의사결정을 위해
필요한 이해관계자들에게 필요하고 정확한 정보를 제공할 수 있어야 한다. 그러나 이와
같은 정보를 권한이 없는 사용자가 부정한 방법으로 가로채거나 부적절하게 기록하게
되면 해당 정보를 필요로 하는 사람이나 개인에게 커다란 피해를 입힐 수 있다. 그래서
권한이 없는 사용자의 부적절한 접근을 막고 동시에 정당한 권한을 가지고 있는 사용자
는 정보시스템이 서비스 요구를 거부하지 않도록 보호할 필요가 있다. 데이터베이스 보
안 필요성을 다음과 같은 항목에 대하여 분석한다.
(가) 데이터의 자산 가치 증가
(나) 내부자에 의한 정보 유출 및 보안 사고 급증
(다) 개인정보 유출에 대한 불안감이 높아지거나 신뢰성 저하
(라) 피해 규모 확산 속도가 늘어나거나 막대한 사회적 비용 발생
(마) 데이터베이스 정보보호에 대한 국내·외 법률 동향
(바) 현행 데이터베이스나 IT 보안 체계의 취약성 존재
(사) 상용 DBMS의 보안 취약성
(아) 애플리케이션 구축 및 운영에서의 보안약점
3. 데이터 무결성 규칙의 종류를 활용하여 분석한다.
(1) 도메인 무결성 규칙을 분석한다.
(가) 테이블 내의 모든 행(row)에 관한 무결성 법칙이다.
(나) 데이터 형태, 범위 검사, 기본값, 유일성 등에 관한 제한을 말한다.
(다) 주어진 속성값이 그 속성에 정의된 도메인에 속한 값이어야 한다는 규정에 의하여 삽입
이나 갱신 연산에 적용된다.
(2) 실체 무결성 규칙을 분석한다.
(가) 기본 키(primary key)는 널(null) 값을 가질 수 없다.
(3) 참조 무결성 규칙을 분석한다.
(가) 외래 키(foreign key) 제약 조건을 분석한다.
(나) 릴레이션을 조작하는 과정에서 의미적 관계를 나타내는 것을 분석한다.
(다) 삽입이나 삭제 또는 갱신과 같은 연산을 수행하기 전과 후에 대한 관계를 규정한다.
(라) 외래 키가 있는 테이블의 경우, 외래 키의 값은 null이거나 관련 테이블에 이와 대응하
는 기본 키가 있어야 한다.
(4) 트리거를 분석한다.
(가) 무결성 규정은 위반 시 단순한 트랜잭션을 취소시킨다.
(나) 트리거는 트리거 조건이 만족되는 경우에 취해야 하는 조치를 나타낸다.
(다) 무결성 규정은 트리거의 특수한 경우로 볼 수 있다.
4. 데이터베이스 보안요구사항을 분석한다.
발생 가능한 위협으로부터 데이터베이스를 보호한다는 것은 우연이든 고의적이든 비권한자
의 정당하지 않은 읽기 접근이나 변경으로부터 저장 데이터를 보호하는 것을 뜻한다.
데이터베이스 보안요구사항 분석은 다음의 몇 가지 종류의 분야에서 중점적으로 분석한다.
(1) 권한을 부여받은 사용자만 접근을 허용하고 있는가?
(2) 추론 방지가 요구되고 있는가?
(3) 데이터베이스의 무결성이 보장되도록 하고 있는가?
(4) 데이터의 논리적 일관성이 보장되고 있는가?
(5) 감사 기능이 제공되고 있는가?
(6) 사용자 인증이 적정하게 이루어지고 있는가?
(7) 시스템 간 데이터의 전송 제한이 이루어지고 있는가?

(cid:49684) 데이터베이스 보안 설계
데이터베이스 보안은 내부 및 외부자가 데이터베이스 내에 저장된 조직의 주요 기밀 정보에 불
법적으로 접근하는 것을 막는 것이다.
데이터베이스에 저장된 데이터를 인가하지 않은 변경이나 파괴, 노출 및 비일관성 등을 발생시
키는 외부의 위협들로부터 보호하는 것이다. 즉, 데이터베이스 보안 설계는 정보 보안의 범주
에서도 데이터베이스에 저장된 데이터 보호를 위한 설계에 초점을 맞춘 것이다.
이러한 데이터베이스의 보안 위협들은 사용자의 실수나 오용, 내부 사용자의 권한 남용이나 비
정상적인 접근 및 데이터베이스에 대한 알려진 취약점들로부터 시작된다.
(cid:49685) 데이터베이스 보안 설계 시 고려하는 주요 위협 요소
데이터베이스에 대한 보안 설계 시 고려하여야 하는 위협 요소의 종류를 다음과 같은 항목으로
살펴보고 보안 데이터베이스의 설계 시 참고하여 보안 요소가 가미된 데이터베이스 설계가 되
도록 한다.
1. 일반적인 데이터베이스 위협
데이터베이스 보안 위협으로는 SQL injection, 악성 프로그램 삽입 등을 통해 외부의 인가되
지 않은 사용자가 악의적인 목적을 가지고 데이터베이스의 중요 정보를 유출하는 것이 있다.
SQL injection 공격은 입력값에 대한 검증 미비로 인한 위협으로 로그인 인증을 우회하여,
데이터베이스 데이터를 열람 및 유출하거나 데이터베이스 서버에 시스템 명령을 실행하는
것이 가능해지고, 파일 업로드에 대한 취약점이 존재할 경우 웹 셸(web shell) 등을 실행하
여 데이터베이스의 데이터에 접근한다.
2. 사용자에 대한 식별 및 인증 위협
사용자 식별 및 인증은 데이터베이스에 접근하기 위한 가장 기본적인 단계이다. 취약한 인
증 수준과 식별되기 쉬운 비밀번호의 사용은 사전 공격(dictionary attack), 무작위 대입
공격(bruteforce attack), 사회 공학적 기법(social engineering)에 의하여 쉽게 노출되는
경우가 있다.
<표 1-7> 비밀번호 공격 기법
기법 설명
사전 공격 일반적으로 사용되는 단어나 단어 조합으로 구성된 암호는 사전(dictionary)
(dictionary attack) 의 단어를 순차적으로 입력하여 사용자 암호를 알아낼 수 있는 기법
무작위 대입 공격 가능한 모든 값(문자, 숫자, 특수기호 등)을 무작위로 반복적으롤 대입하여
(bruteforce attack) 사용자 암호를 알아내는 기법
사회공학적 기법 컴퓨터 시스템이 아닌 미흡한 보안관리로 인하여 인쇄물, 필기, 녹화화면 등
(social engineering) 에서 암호를 알아내는 기법으로, 지속적으로 암호를 알아내기 위한 행동
3. 데이터 유출 위협
암호화되지 않은 데이터는 네트워크 도청, 파일 백업 그리고 정당한 사용자 및 인가되지 않
은 사용자에 의한 데이터베이스 검색 등을 통하여 데이터가 유출될 수 있다. 또 암호화된
데이터의 경우도 안전성이 확인되지 않은 암호 모듈을 사용하는 경우 악의적인 사용자에
의하여 암호문이 해독되는 경우가 있다.
4. 권한 오남용 위협
데이터베이스의 데이터 접근 권한이 업무 사용을 위해 허용된 권한보다 더 많이 부여되거
나 정당한 사용자가 악의적인 목적으로 허용된 범위를 넘어서 인가되지 않은 작업을 수행
하는 경우에 권한이 오남용되어 데이터 유출 또는 데이터 위·변조가 발생할 수 있으며, 시
스템의 취약점을 이용하여 불법 권한 상승 및 계정 정보를 획득하는 경우가 있다.
5. 암호 모듈 오용 위협
데이터베이스의 데이터를 암호화하기 위해 안전성이 검증되지 않은 암호 모듈을 사용하거
나, 적합하지 않은 암호 모드를 사용하는 경우 암호문이 해독될 수 있다. 데이터가 한 블록
이상의 크기를 가지는 경우 블록 암호 알고리즘을 적용하면 사전 공격에 의해 해독될 수
있으며, 동일 평문에 대하여 동일 암호문이 생성되면 암호문을 통해 암호 키를 추측하는 경
우가 있다.
6. 암·복호화 키 및 마스터키 노출 위협
데이터 암호화 시 키가 노출되면 암호화된 데이터를 복호화할 수 있기 때문에 키를 안전하
게 관리하는 것은 매우 중요하다. 따라서 데이터를 암호화하는 경우 키가 인가되지 않은 제
3자에게 노출되지 않도록 안전하게 보관하여야 하며, 암·복호화 키는 마스터키를 통하여 암
호화되어 실제 사용 시점에만 임시로 복호화하여 사용하여야 한다.
암·복호화 키가 노출되는 경우 키 변경을 통하여, 신규 데이터는 변경된 키를 사용하여 암
호화하고 기존 암호문의 경우도 마이그레이션 작업을 통하여 신규 암호문으로 변경하는 등
키 노출에 대한 보호 방안을 고려하여야 한다.
7. 프로젝트 수행 과정에서의 데이터베이스 접근 허용 위협
프로젝트 수행 과정에서 프로젝트에 참여한 외부 작업자가 자사의 데이터에 접근할 수 있
는 권한을 부여함으로써 데이터 유출이 발생한다.
프로젝트 목적상 데이터베이스를 사용해야 하는 경우, 보안서약서를 작성하게 하고 추가적
인 물리적인 보안 통제를 적용함으로써 정보 유출을 방지하는 절차가 있어야 한다.
8. 운영 과정에서 권한에 대한 관리 소홀로 인한 침해 발생 위협
개발자에게 DBA 권한을 설정함으로써 개발자가 직접 데이터베이스에 접근하여 정보 유출이
가능하다. 잘못된 사용자 권한 설정으로 비정상적인 데이터 노출 및 외부 유출이 발생한다.
9. 접근 통제 우회
DBMS 도입 시 설정되는 디폴트(default) 계정 또는 단순 계정 등 계정 번호(ID)와 비밀번
호가 동일할 경우 암호 추측 공격, 사전 공격 등을 통해 계정을 확인할 수 있으며, 이를 통
해 데이터베이스의 자료 유출 및 변조 등이 발생할 수 있다. 계정 및 패스워드의 정책 설정
이 미흡한 경우 무차별 공격에 의해 패스워드가 크래킹 되는 경우가 있다.
10. 데이터베이스 정보의 불법 열람 및 변조·삭제 위협
데이터베이스에 저장된 주요 정보에 대해 암호화가 미흡한 경우 비인가자에 의해 정보가
노출되거나 변조될 수 있다. 현재의 침해사고 추세를 볼 때 데이터베이스에 저장된 개인정
보, 금융 관련 정보, 게임 관련 정보를 탈취하려고 하는 시도가 증가하고 있어 데이터베이
스의 보안에 대한 요구사항이 증가하고 있다.
상용 데이터베이스 서버에 공개키(PKI: public key infrastructure) 기반의 강력한 암호화
기능과 검증 기능을 제공함으로써 기존 데이터베이스에 대한 불법적 접근을 방지하여야 한
다. 또 사용자가 데이터베이스의 내용을 추출하여도 암호화된 상태의 데이터베이스 기밀성
이 유지되는 시스템을 구축하여야 한다. [그림 1-8]은 사용자별 차등 접근 권한 부여 개요
를 나타내고 있다.

1. 데이터베이스 접근제어를 설계한다.
(1) 정보 식별(right information)을 식별한다.
접근제어를 할 대상 정보를 파악한다. 다음은 정보 식별의 대상이 되는 항목이다.
(가) 데이터베이스
DBMS에서 관리하고 있는 데이터이다. 정보의 가장 큰 단위에 속하게 되며, 일반적
으로 데이터베이스 단위보다는 더 세밀하게 접근제어를 수행해야 한다.
(나) 데이터베이스 계정
데이터베이스 정보에 접근 가능한 계정이다. 데이터베이스 종류에 따라 단순히 데이
터베이스에 로그인할 수 있는 계정일 수도 있고, 테이블이 생성된 스키마를 의미할
수도 있다. 시스템에 따라 정보에 접근하는 통로의 의미를 가지는 논리적 계정과 실
제로 테이블을 소유권을 가지고 있는 물리적 계정이 분리되어 있는 경우가 있다.
(다) 테이블/뷰
데이터베이스에서 정보가 저장되어 있는 논리적인 집합체이다. 테이블은 물리적으로
데이터를 보관하고 있는 실체이지만, 뷰는 테이블을 바탕으로 정보를 재구성했지만 실
제로 데이터를 관리하지는 않는 논리적 실체이다. 다만 데이터베이스 접근제어는 데이
터베이스 서버 외부에서 접근제어를 구성하므로 SQL 분석 단계에서 테이블과 뷰를 구
별할 수 없는 제품이 많으므로, 뷰와 테이블 모두 규칙을 정의해 준다.
(라) 칼럼
테이블에 소속된 정보의 일부 속성값. 주민등록번호, 성명, 급여 정보 등과 같이 매
우 민감한 정보의 경우에는 칼럼 단위로 통제를 해야 한다.

도의 ID와 패스워드를 부여하여 추가로 인증을 수행한 후에 로그인하도록 한다.
(3) 접근 방법(right form) 식별 작업을 한다.
정보에 접근할 수 있는 방법을 정의한다. 데이터베이스 사용자들이 데이터베이스에 접속
하기 위해 사용할 수 있는 단말기, 접속 툴, 접속 프로토콜 등을 지정한다. DBA나 운영
자의 경우에는 모든 종류의 SQL을 수행하도록 권한을 부여하고, 각 정보에 관리 책임이
있는 담당자는 SELECT, UPDATE, DELETE, INSERT, COMMIT, ROLLBACK 등의
명령 수행이 가능하도록 한다. 기타 일반 사용자에게는 SELECT 문장만 수행하게 하여
제한을 두는 방법 등으로 제한한다.
(4) 접근 시간(right time) 식별 작업을 한다.
정보에 접근할 수 있는 시간을 통제하는 작업을 한다. 특별히 민감한 정보는 업무 시간
에만 접속이 가능하도록 설정하는 방법이 있고, 그 외에 해당 정보에 접근하는 경우에는
차단하거나 시스템 관리자에게 경보를 발령하도록 하는 방법을 사용한다.
2. 데이터베이스 암호화를 설계한다.
데이터베이스 암호화를 구축하기 위해서는 복호화 권한 통제, 암호 키 정의, 그리고 암호화
키 사용에 대한 로깅 등을 고려하여 설계한다. 암호화 규칙은 데이터베이스를 암호화하기
위한 기본적인 전제 조건과 고려 사항을 언급한 것이며, 암호화를 규칙대로 적용하고 암호
화 후 정상적인 데이터베이스 서비스를 지속시키기 위한 몇 가지 지표는 다음과 같다.
• 데이터베이스에 접속할 수 있는 사용자에 대한 정의
• 데이터베이스에 접속하는 사용자 식별에 대한 방법
• 암호화 대상 칼럼의 범위 정의
• 암호화 칼럼에 대한 복호화 권한 통제 수행
• 암호화 키를 위한 알고리즘과 대상 정의
• 암호화 키 사용에 대한 로깅 수행
(1) 복호화 권한을 통제한다.
데이터베이스 칼럼(column)에 대한 암호화가 수행되면 인가된 사용자에게 복호화된 평
문 데이터(plain data)를 전송한다. 그러나 인가되지 않은 사용자에게는 암호화된 데이
터나 일부 암호화된 데이터를 전송한다.
(가) 사용자 식별
데이터베이스에 접근하는 경우는 다음과 같다.
1) 웹(web)이나 애플리케이션 서버(application server)의 정형적인 접근
2) 데이터베이스 관리자에 의한 비정형 접근
3) 프로그램 개발자나 유지보수 지원 엔지니어에 의한 비정형 접근
(나) 암호화 대상 칼럼
데이터베이스 칼럼 암호화는 개인정보나 민감 정보가 저장된 테이블의 칼럼 정보를
비인가자로부터 보호하는 것이다. 암호화 대상 칼럼의 경우 DBMS에서 지원하는 다양
한 종류의 데이터 타입을 가지는데, 일반적으로 개인정보의 이름, 주소, 생년월일, 카
드번호, 이메일 주소 등 문자형(스트링(string))이 칼럼 암호화 대상으로 제일 많다.
(다) 암호화 칼럼에 대한 복호화 권한 통제
암호화의 대상은 다수의 테이블에 존재하는 여러 칼럼이다. 하나의 테이블에 존재하
는 서로 다른 칼럼이라도 사용자를 식별하여 복호화한다. 대게 테이블과 칼럼은 하
나의 데이터베이스 사용자에 의해 소유되지만, 데이터베이스 계정은 여러 사용자에
의해 공유되는 경우가 있기 때문이다.
(라) 비인가 사용자에 대한 통제
암호화된 데이터는 인가된 사용자나 시스템에는 정상적인 복호화 데이터를 전송하지
만, 비인가 사용자에게는 암호화된 데이터나 일부 암호화 데이터를 전송한다.
(2) 암호화 키 및 알고리즘을 이용하여 구현한다.
암호화 키는 암호화 알고리즘(encryption algorithm)과 파라미터 키(parameter key)
의 조합으로 이루어진다. 암호화 방식은 대칭형(symmetric)과 비대칭형(asymmetric)
방식이 있는데, 대칭형은 암호화 키와 복호화 키가 동일하고, 비대칭형은 암호화 키와
복호화 키가 다르다. 대표적인 암호화 알고리즘으로 대칭형 알고리즘은 DES, 3-DES,
AES, SEED, ARIA, MASK가 있고, 비대칭형 알고리즘은 RSA, DSA가 있다. 프로젝트
및 데이터 성격에 따라 알고리즘을 선택하여 사용한다.

3. 데이터베이스 작업 결재를 설계한다.
데이터베이스 작업 결재의 핵심은 어떤 SQL을 수행하거나 어떤 정보에 접근할 때 결재를
받아야 하는지와, 결재를 누구에게 받느냐인 것이다.
(1) 결재 대상을 정의한다.
(가) 사용자 중심 정의
작업 결재를 받아야 하는 대상을 사용자 중심으로 설정한다. 사용자를 그룹으로 설
정할 수도 있고, IP, 사용 툴 등의 조합으로 정의하기도 한다.
(나) 정보 중심 정의
SQL을 통해 접속하고자 하는 정보를 중심으로 설정한다. 즉 중요한 정보에 접근할
경우에는 접근하는 사람에 상관없이 항상 결재를 받는 경우와 같이 정의한다.
(다) SQL 중심 정의
특정 종류의 SQL을 수행하는 경우에 결재를 수행하도록 한다. 즉, DROP,
TRUNCATE 등의 스키마 구조에 중대한 영향을 미치는 명령이거나, GRANT 등의
권한 설정에 중대한 영향을 미치는 SQL에 대해서만 결재를 수행하도록 하는 방식이
다. SQL 단위로 결재를 받는 경우에는 SQL에 대한 수행 횟수에 대해서도 통제할
수 있다. 즉, 특정 SQL에 대하여 몇 회(예를 들면 10회)까지만 반복하여 수행할 수
있도록 제한하는 것이다.
(2) 결재자를 정의한다.
결재를 수행할 결재자를 정의하는 것이다. 결재는 특정인이 수행할 수도 있지만, 결재
라인을 구성하여 다수의 결재자가 순차적으로 결재를 진행하도록 설정하는 경우가 대부
분이다.
또 특정 분야는 A 결재 경로를 통해 결재를 진행하고, 다른 분야는 B 결재 경로를 통해
결재를 진행하도록 설정하는 경우도 있다.
(3) 결재 사용자 관리를 한다.
결재 시스템 사용을 위한 사용자 관리를 한다. 즉시 결재의 경우에는 데이터베이스 접근
제어와 사용자를 공유한다. 그러나 사전 결재 및 사후 결재는 데이터베이스 접근제어에
서 제공하는 결재 시스템을 사용할 수 있지만, 별도의 결재 시스템을 이용하여 구현할
수도 있다. 데이터베이스 접근제어의 인증 기능을 이용하여 사용자를 식별하는 경우에는
데이터베이스 접근제어 방법에 따라 사용자를 관리한다.
(4) 결재자 관리를 한다.
결재를 수행할 결재자에 대한 관리를 한다. 결재자는 결재 경로를 통해 결재자로 지정된
다. 결재자가 결재를 할 수 없을 경우, 이를 인지할 수 있는 기능과 다른 사람에게 결재
를 위임할 수 있는 기능도 필요하다.

4. 데이터베이스 취약점을 분석하고 설계한다.
데이터베이스의 취약점을 보안 관리자 또는 DBA가 찾아낼 수도 있지만, 이는 많은 시간과
노력이 필요하다. 이를 극복하고 업무의 효율성을 높이기 위해 데이터베이스 취약점 분석용
전문 솔루션을 사용한다. 이는 빠른 시간에 방대한 데이터베이스를 분석하여 취약점을 찾아
내서 해당 데이터베이스의 보안 대책을 세우는 기초 자료를 제공한다.

[그림 1-12] 취약점 분석 절차
(1) 데이터베이스 환경을 적정하게 구축한다.
데이터베이스 설치 항목 중 필요한 요소가 무엇인지 확실하지 않다면 일반적인 구성으
로 설치하게 되는데, 대체로 데이터베이스의 대표적인 취약점은 사용하지 않는 모듈의
취약점을 통해 공격하는 사례가 많아 데이터베이스를 처음 설치할 때에는 필요한 구성
요소만 설치한다.
(2) 계정 관리를 한다.
제일 많이 사용하는 데이터베이스를 설치하면 다수의 디폴트 사용자 계정이 생긴다. 만
약, 수동으로 설치하는 경우라면 디폴트 사용자 계정은 모두 열린다. 즉, 잠기지 않는
상태가 되므로 주의가 필요하다. 이러한 이유로 수동으로 설치한 데이터베이스는 SQL문
을 통하여 디폴트 사용자 계정을 잠그고 기간을 만료시킨다. 특정 사용자 계정을 잠그고
기간을 만료시키는 SQL 문장은 다음과 같다.
SQL> ALTER USER test ACCOUNT LOCK PASSWORD EXPIRE;
(3) 패스워드 관리를 한다.
디폴트 사용자 아이디인 SYS, SYSTEM 사용자 계정들은 패스워드를 변경해 주어야 한
다. 데이터베이스를 공격하는 가장 손쉬운 방법은 설치 당시의 디폴트 패스워드를 사용
하는 사용자 아이디를 사용하는 것이므로 패스워드의 변경은 설치 직후에 반드시 수행
한다.
(4) 권한 관리를 한다.
사용자는 반드시 필요한 최소 권한만을 부여한다. PUBLIC 사용자 그룹에서 불필요한 권한
을 회수한다. PUBLIC은 데이터베이스의 모든 사용자에게 디폴트로 적용된다. 따라서 모든
사용자는 PUBLIC에 권한 부여된 것은 어떤 일이든 할 수 있다. 이런 경우 사용자가 SQL
패키지를 실행시켜 자신에게 권한 부여된 권한 범위를 넘어서는 작업을 하는 경우가 있다.
(5) 인증 관리를 한다.
클라이언트에 대한 철저한 인증이 필요하다. 그러나 일반적으로 개인 컴퓨터의 경우에는
적절한 인증 여부를 보장할 수 없다. 따라서 원격 인증 기능을 사용하면 보안이 대단히
취약하다. 원격 인증 기능을 비활성화한다면 데이터베이스에 접속하려는 클라이언트들은
서버 기반 인증을 해야 하므로 보안이 강화된다. 원격 인증을 제한하여 클라이언트의 인
증을 데이터베이스 서버가 행하도록 하려면 파라미터 파일의 내용을 다음과 같이 수정
하여 바꾸어 준다.
REMOTE_OS_AUTHENTICATION = FALSE
또 데이터베이스 서버가 있는 시스템의 사용자 수를 제한한다.
(6) 원격 접속 관리를 한다.
(가) 방화벽 구축
데이터베이스 서버는 방화벽 뒤에 설치한다.
(나) 기본 서비스 포트 사용 자제
패스워드 설정 없이 데이터베이스를 운영한다면 데이터베이스에 대한 중요한 정보들이
노출된다. 이러한 노출 정보가 많으면 많을수록 데이터베이스가 공격당할 가능성이 높
아진다.
(다) 네트워크 트래픽(network traffic) 암호화
데이터베이스 서버와 클라이언트의 통신은 암호화되지 않은 형태로 이루어지는 경우가
많다. 이는 네트워크상의 악의적인 공격자에 의해 데이터의 읽기, 변경, 삭제 등의 변조
가 가능하다는 위협이 존재한다. 따라서 네트워크 트래픽을 암호화해야 한다.
(라) 데이터베이스 서버가 있는 시스템의 운영체제 강화
서버에서 불필요한 서비스를 없애면 데이터베이스 서버 시스템이 보다 안전해진다. 유
닉스(uxix)와 윈도(windows)를 막론하고 ftp, tftp, telnet 등의 불필요한 많은 서비스
들을 제공하는데 제거된 서비스가 사용하는 TCP/UDP 포트를 반드시 모두 막는다.
(마) 보안 패치의 적용
데이터베이스가 운영되고 있는 운영체제와 데이터베이스 자신에 대한 모든 중요한
패치를 정기적으로 실시한다. 조직 차원에서 패치와 관련된 업무 프로세스를 만들어
사용하면 좋다.
(cid:49685) 데이터베이스 보안 프레임워크를 고려하여 설계를 실시한다.
1. 데이터베이스 보안 프레임워크 구성 요소를 고려한다.
데이터베이스 보안 프레임워크는 데이터베이스 보안 기술 요소와 데이터베이스 보안 구축

[그림 1-15] 데이터베이스 구현 절차
1. 데이터베이스 생성 준비
데이터베이스 구현 작업을 실시하기 전에 관련 산출물이나 도구, 서버의 상태 등을 확인한다.
2. 데이터베이스 생성
서버의 명령어나 SQL을 이용하여 데이터베이스를 생성하고 구현한다.
3. 테이블 스페이스 생성
테이블 스페이스(table space)는 데이터베이스 오브젝트 안에 데이터를 저장하는 공간이다.
이것은 데이터베이스의 물리적인 부분이며, 세그먼트로 관리되는 모든 DBMS에 대해 저장
소(세그먼트)를 할당하여 사용한다. 데이터베이스 세그먼트는 데이터베이스 오브젝트 중의
하나이며, 테이블이나 인덱스와 같이 물리적 공간을 사용한다. 테이블 스페이스는 한번 생
성되면, 데이터베이스 세그먼트 생성 시 이름으로 참조된다.
테이블 스페이스가 파일시스템에 데이터를 저장하는 것이 일반적이고 일부 DBMS는 raw
device로 불리는 OS device로 구성하여 운영체제 파일시스템의 오버헤드를 없애고 더 빠
른 성능을 제공하는 방법을 사용한다.
4. 사용자 생성
데이터베이스에 접속하여 사용하게 되는 사용자 ID를 생성하고 각 사용자별로 권한을 설정
하는 단계이다.
(cid:49685) 데이터베이스 접근 통제
데이터베이스 접근 통제는 사용자가 DBMS에 접근하거나 SQL을 수행하려고 할 때 미리 정의
된 보안 규칙에 따라 권한 여부를 판단하여 통제하는 것이다,
데이터베이스 접근 통제는 데이터베이스에 접근하는 네트워크 패킷을 분석하는 기술로 게이트

(다) 암호 키가 물리적으로 안전한 장소에 저장되어 있고 권한이 부여된 사용자에 의해서만
접근이 가능한지 점검한다.

• 암호화 알고리즘(3DES, ARIA, SEED, AES, TDES, SHA-1, RSA(PKCS#1),

• 암호화 가능 칼럼 타입(CHAR, VARCHAR, VARCHAR2, DATE, INT, NUMBER,
FLOAT, LONG, LOB 확인)
• Index column 지원
• PK/UK/FK column 지원
• Trigger 및 default values 지원
• Null Value 지원
• Partitioned table (Range, Hash, List partitioned) 지원
• 운영체제 환경에 독립적
• 칼럼 데이터의 부분 암호화 지원(앞뒤 N자리)
• 운영체제 및 DBMS의 업그레이드에 독립적
• 백업 및 복구, 운영자 관리, 리포트 분석 등 다양한 관리 체계
3. 데이터베이스 작업 결재를 숙지한다.
(1) 우회 접근 방지를 숙지한다.
작업 결재를 거쳐서 수행해야 하는 SQL이 데이터베이스 작업 결재 시스템을 우회하여
수행할 수 없도록 방지한다. 작업 결재가 데이터베이스 접근제어와 결합되어 구축되어
있어야 한다.
(2) 작업 환경 구축을 실시한다.
데이터베이스 작업 결재 시스템은 데이터베이스 접근제어와 결합되어 구성되거나, 결재
시스템을 별도로 외부의 시스템을 사용하여 구축한다.
(3) 데이터베이스 작업 결재 보안 규칙을 적용한다.
(가) 이력 관리 구성 요소 구축을 실시한다.
1) 데이터베이스에 접근할 수 있는 사용자들에 대한 IP, ID, 성명, 조직, 연락처 등에
관한 정보
2) 결재자, 결재선 구성에 대한 정보
3) 사용자가 접속할 수 있는 데이터베이스에 대한 정보
4) 작업 결재 규칙 정보
(나) 백업 관리를 실시한다.
데이터베이스 작업 결재에 대한 백업을 한다. 보안 정책은 일정 시간 동안 변경될
수 있으므로 주기적으로 백업을 실시한다. 특성에 따라 별도의 보안 정책 저장 기능
을 제공하고 로그와 같이 일괄적으로 백업하여 관리한다.
(다) 사용자 로그 관리를 실시한다.
결재 문서는 기안 단계에서 승인 과정에 이르는 모든 이력과 승인된 문서에 포함된
SQL의 수행에 이르는 모든 과정을 저장한다. 데이터베이스 결재 시스템에서 관리하
는 로그의 종류는 다음과 같다.
1) 결재 시스템에 로그인한 정보
2) SQL을 포함하여 결재 기안된 경우에는 해당 SQL 정보를 저장하고, 사전/사후 정
보를 같이 생성한 경우에는 해당 정보도 로깅
3) 대리 결재/긴급 결재/사후 결재 등의 다양한 결재 이력 저장
4) 승인된 결재 문서의 SQL을 수행한 이력 정보
5) 결재를 받도록 통제하는 규칙 정보
6) 경보가 발생한 이력 정보
7) 권한이 없는 SQL 수행을 차단한 이력
(라) 모니터링을 실시한다.
데이터베이스 작업 결재와 관련된 모니터링은 작업 결재 과정에 문제가 없는지 확인
하는 기능이다. 얼마나 많은 문서가 결재를 위해 만들어졌는지, 결재 과정에 있는 문
서들은 어떤 단계에 있는지, 결재가 늦어지고 있는 문서들은 얼마나 되는지 등의 정
보를 쉽게 파악할 수 있도록 그래픽 기반의 화면을 제공하기도 한다.

[그림 2-1] 데이터베이스 보안 범위
1. 애플리케이션
애플리케이션의 범위는 웹 애플리케이션이나 조직 내 애플리케이션과 같이 데이터베이스를
액세스하는 모든 애플리케이션을 포함한다. 이는 데이터베이스와 직접적인 작업 여부를 기
준으로 SQL 부분, SQL을 포함하는 프로그램 모듈, 데이터베이스 내의 기능이나 패키지를
호출하는 부분은 제외한다.
2. 네트워크
데이터베이스 서버의 네트워크 인터페이스는 데이터베이스 서버 영역으로 분류하여 통제하
여야 한다.
3. 데이터베이스 서버 영역
(1) IP 기반의 접속 통제
데이터베이스 서버의 네트워크 인터페이스에서는 데이터베이스 자체 혹은 운영체제에서
제공하는 기능을 사용하여 IP 주소나 MAC 주소를 기반으로 하는 필터링을 구현하여야
한다. 접속을 허용하는 IP는 WAS 서버와 DBA용 노드 및 기타 필요한 최소 노드만을
허용하여 기타 노드로부터의 우회 접속을 차단하여야 한다. 각 접속 현황의 로그 경로를
생성하고 수시로 모니터링하여 비허용 IP의 연결 시도를 감지하여야 한다.
(2) 운영체제와 데이터베이스의 독립화 및 실행 파일 보안
데이터베이스 서버에 설치된 운영체제와 DBMS는 최대한 독립이 이루어져야 한다.
DBMS에 따라 다르지만 대부분의 운영체제에서 제공하는 기능들은 DBMS에서도 제공
된다.
운영체제의 공격이 성공으로 이루어진다면 데이터베이스의 공격을 방어할 수 있는 방법
이 많지 않은데, 다음의 방법은 이를 조금 더 어렵게 할 수 있다.
(가) 운영체제의 관리자 계정과 데이터베이스의 관리자 계정 및 소속 그룹은 독립적으로 설계
되어야 한다.
(나) DBMS에 해당하는 모든 실행 파일과 데이터가 저장되는 파일 및 폴더에 대한 권한 또
한 최대한 독립적으로 구성되어야 한다.
(다) DBMS와 관련된 실행 파일들의 소유자 권한을 최소화해야 한다.
(라) 운영체제와 DBMS를 설치할 때 불필요한 가능들은 최대한 배제한다.
(마) DBMS의 직접적인 설정을 제어하거나 운영에 필수적인 파일들을 대상으로 변조를 감지
하기 위하여 수시로 체크섬(checksum) 검증을 한다.

(cid:49684) 데이터베이스 보안 침해
데이터베이스를 공격하는 공격자들이 갖는 공격 목표 및 방법은 무한대의 조합이 가능하므로
완벽한 정보 보안의 구축은 매우 어려운 문제이다. 공격자는 공격 목표를 달성하기 위해 접근
가능한 모든 침투 수단을 탐색하게 되고 각 단계별로 보안 수준에 대한 취약점을 파악하고 침
투가 용이한지를 판단한다.
이러한 경우 공격자가 강력한 보안 대책이 방어하고 있는 경로를 통한 침투를 시도하기보다는
공격 대상의 취약점을 통한 손쉬운 침투 경로를 선택하게 된다.

[그림 2-6] 데이터베이스 보안 침해 대응
취약점은 알 수 없거나 알려지지 않은 것들로 인해 발생하게 되므로 어떠한 정보시스템도 완벽
하게 자산을 보호할 수는 없다. 정보시스템은 공격자의 위협(threat) 행위에 이용될 수 있는 논
리적인 형태 또는 물리적인 형태의 취약점들을 가진다.
공격자는 정보시스템의 대응책에도 불구하고 존재하는 취약점인 틈새를 탐지하게 되고, 공격자
에게 노출된 취약점이 정보시스템에 위협이 된다. 즉 공격자는 취약점을 이용하여 위협 행위인
공격을 수행한다.
1. 취약점
정보시스템의 설계, 구현, 처리 또는 관리에 있어 자원이 가지는 보안상의 결점을 의미한다.
정보시스템 설계에 보안상의 모든 위험 요인들을 고려하여 대비해야 하지만, 취약점은 예측
하지 못한 상황에서 매우 다양한 형태로 발생한다. 어떠한 취약점들이 존재하는지에 대한
이해가 필요하다. 취약점의 범주는 소프트웨어, 프로시저 결함, 구성원 역량, 서비스 환경으
로 구분된다.

[그림 2-7] 취약점 구성 요소
(1) 소프트웨어
시스템 운영을 위해 활용되는 모든 응용프로그램, 운영체제, DBMS, 각종 툴 등 소프트
웨어 자체가 갖는 결점으로 인해 존재하는 취약점이다.
(2) 프로시저 결함
시스템의 분석, 설계, 구현, 그리고 운영에 이르는 전 과정에서 보안 정책과 절차에 대
한 조직 차원의 지침이 미비하여 발생하는 취약점이다.
(3) 사용자 역량
보안에 있어 가장 민감한 요인은 사람이며 모든 보안 취약성과 관련을 갖는다. 보안에
대한 전문성의 부족, 보안 운영 절차를 미준수, 구현에 있어 부주의나 예외 상황에 대한
처리 미정의 등으로 인해 발생하는 취약점이다.
(4) 서비스 환경
천재지변이나 자연재해, 신뢰할 수 없는 컴퓨터 하드웨어, 전원 공급, 통신 선로, 정보
저장소 등으로 인해 발생하는 취약점이다.
2. 위협
정보시스템의 자원이 갖는 취약점으로 인해 잠재적인 위험이 존재하는 사건이나 상황을 의
미한다. 공격 대상 시스템에 잠재하는 취약점을 대상으로 수행되는 위협 행위도 취약점의
범주에 따른 사례만큼 다양한 형태로 분류된다. 위협의 범주는 소프트웨어 코드, 사용자, 고
장, 자연 현상으로 구분된다.

해를 말한다.
(cid:49685) 데이터베이스 보안 위험 관리
악의적인 공격자나 기타 사용자의 실수 등으로 인해 발생하는 보안상의 취약점이나 위협들로부
터 기술적으로 완벽한 보안을 제공한다는 것은 현실적으로 불가능하다. 일반적인 시스템들은
소프트웨어 오류나 잘못된 설정, 보안상의 결함으로 인해 취약할 수밖에 없는데, 정보시스템의
빈틈은 공격자가 침투할 수 있는 여지를 제공하여 보호되어야 하는 주요 자산을 공격자에게 넘
겨주는 상황이 발생하기도 한다.
데이터베이스 자원에 존재하는 취약점과 위협 요인들을 식별하고, 자산의 가치에 근거하여 수
용 가능한 수준의 위험 감소 방안 및 절차가 요구되는데, 이를 위험 관리 절차로 관리한다. 위
험 관리 절차는 순환적으로 반복적으로 수행되어야 한다. 위험을 관리하기 위한 대응 방안들은
보호되어야 하는 데이터베이스 자산의 가치에 견주어 생산성, 비용, 효용성 등의 균형을 유지
해야 한다. [그림 2-9]는 데이터베이스 보안 관리의 절차를 나타내고 있다.

4. 실행
생산성, 비용의 효율성, 자산의 가치 등을 고려한 영향 평가를 통해 산출된 계획에 따라 적
절한 대응 방안을 적용하는 단계이다.
5. 감시
생산성 저하를 최소화할 수 있는 최적화된 방어 비용을 기반으로 통제 수단을 적용하고 효
용성을 평가하는 단계이다.

(2) 패킷 손실(Packet Loss) 시험을 실시한다.
스니핑 방식으로 로깅 하도록 설치한 경우에는 스니핑의 특성상 패킷 손실이 발생할 수
있다. 그리고 구성상의 오류나 시스템의 사양이 부족하여 패킷 손실이 발생할 수 있다.
현재 설치된 서버에 패킷 손실이 발생하는지, 얼마나 발생하는지 여부를 측정한다. 가장
간단한 방법은 SQL을 반복해서 자동으로 수행해 주는 툴을 이용한다.
패킷 손실률 = (손실된 SQL 건수/ 수행한 SQL 건수) * 100
측정된 패킷 손실률은 일정 수준(예를 들면, 0.1%) 이하로 관리한다. 그 이상의 패킷 손
실이 발생하는 경우에는 스니핑 서버의 사양을 높이거나 네트워크 카드를 변경한다. 경
우에 따라서는 스니핑 서버를 교체할 경우도 고려하여야 한다.
(3) Long SQL 시험

크기(예를 들면, 500KB) 이상의 SQL도 수행하는데 최악의 상황을 대비하여 1MB 정도
의 임의의 SQL을 만들어 해당 SQL이 완전하게 저장되는지 시험한다.
(4) 성능 시험
인라인 방식으로 게이트웨이를 구성하거나 스니핑 방식으로 WAS에서 오는 모든 SQL을
수집하는 경우 대량의 트랜잭션 발생 시 부하가 높을 수 있다. 이에 따라 시스템에 부
과될 수 있는 최대의 트랜잭션을 계산하고, 일정 수준(예를 들면, 30%) 정도 여유를 더
주어 가상의 트랜잭션을 발생시켜 무리 없이 잘 관리되는지 확인한다.

않은 외부 사용자에 의한 데이터베이스 침해 공격을 시뮬레이션하는 행위이다. 이 방법은

(나) Brute Forcing, Dictionary Attack, 패스워드 크래킹(password cracking) 기법을 통
해 안전하지 못한 데이터베이스 패스워드 추출 여부 점검
(다) 버퍼 오버플로우 공격에 대한 데이터베이스 서비스 오동작 여부 점검
(라) DoS(denial of service) 공격에 대한 데이터베이스 다운이나 서비스 불가 여부
점검
(마) 데이터베이스의 비정상 설정으로 인한 비정상 침투 경로 존재 여부 점검
(2) 내부 보안 감사(security auditing)를 실시한다.
데이터베이스 내부 보안 감사는 알려진 취약점과 더불어 데이터베이스가 보안상 안전하
게 설치되고 운영되는가를 점검하는 것으로 데이터베이스를 구성하는 File, Table
Space, OS, Role, Grant 등의 다각적 보안 검토를 의미한다. 내부 보안 감사에서의
주요 점검 항목은 다음과 같다.
(가) 패스워드를 포함하는 데이터베이스 사용자 계정 정보
(나) 모든 프로파일(profile)과 각 프로파일의 자원(resource) 정보
(다) 데이터베이스 사용자의 다른 역할(Role)에 부여된 역할 정보
(라) 데이터베이스 내의 모든 역할에 대한 상세 정보
(마) 데이터베이스 사용자의 다른 역할에 부여된 시스템 역할 정보
(바) 데이터베이스 사용자에게 부여된 시스템 권한 정보
(사) 데이터베이스 프로세스와 세션 정보
4. 데이터베이스 취약점 체크리스트를 점검한다.
문제 발생 시 해당 원인을 찾아 신속히 대처하기 위해 사전에 발생할 수 있는 문제들이 어
떠한 것이 있는지 파악하고 있어야 하며, 일단 문제가 발생하였을 경우 운영 환경을 점검하
여 빠른 시간 내에 문제를 해결할 수 있어야 한다. 데이터베이스 전체와 데이터베이스를 구
성하는 파일 및 테이블 스페이스 종류별로 백업, 설정, 모니터링 등의 측면을 구분하여 각
각 점검할 사항들을 점검한다.

결함 관리 프로세스는 결함 관리 생명주기에 따라 구축되고 관리한다. [그림 2-11]은 결함
관리 생명주기를 나타내고 있는데, 이러한 과정을 통하여 결함을 관리한다.
