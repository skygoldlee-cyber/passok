(cid:49684) 형상관리 개념
1. 형상관리의 정의
형상관리(SCM: Software Configuration Management)란 소프트웨어의 개발 과정에
서 발생하는 산출물의 변경 사항을 버전관리하기 위한 일련의 활동으로, 다음과 같은
특성이 있다.
(1) 소프트웨어 변경 사항을 파악하고 제어하며, 적절히 변경되고 있는지에 대해 확인하여
해당 담당자에게 통보하는 작업이다.
(2) 형상관리는 프로젝트 생명주기의 전 단계에서 수행하는 활동이며, 유지보수 단계에서도
수행하는 활동이다.
(3) 형상관리는 소프트웨어 개발의 전체 비용을 줄이고, 개발 과정에서 발생하는 여러 가지
문제점 발생 요인을 최소화하는 것을 목적으로 한다.
2. 형상관리 절차
형상관리는 품질 보증을 위한 중요한 요소로서 다음과 같은 절차를 통해 수행된다.
(1) 형상 식별
(가) 형상관리 대상을 식별하여 이름과 관리 번호를 부여하고, 계층(Tree) 구조로 구분하여
수정 및 추적이 용이하도록 하는 작업으로 베이스라인의 기준을 정하는 활동이다.
(나) 형상관리 대상이 되는 형상 항목은 다음과 같다.
1) 소프트웨어공학 기반 표준과 절차: 방법론, WBS, 개발 표준
2) 소프트웨어 프로젝트 계획서
3) 소프트웨어 요구사항명세서
4) 소프트웨어 아키텍처, 실행 가능한 프로토타입
5) 소프트웨어 화면, 프로그램 설계서
6) 데이터베이스 기술서: 스키마, 파일 구조, 초기 내용
7) 소스코드 목록 및 소스코드
8) 실행 프로그램
9) 테스트 계획, 절차, 결과
10) 시스템 사용 및 운영과 설치에 필요한 매뉴얼
11) 유지보수 문서: 변경 요청서, 변경 처리 보고서 등
(2) 변경 제어
식별된 형상 항목의 변경 요구를 검토, 승인하여 적절히 통제함으로써 현재의 베이
스라인에 잘 반영될 수 있도록 조정하는 작업으로, 적절한 형상 통제가 이루어지기
위해서는 형상통제위원회 승인을 통한 통제가 이루어질 수 있어야 한다.
(3) 형상 상태 보고
베이스라인의 현재 상태 및 변경 항목들의 반영 상태를 보고하는 절차이며 형상의
식별, 통제, 감사 작업의 결과를 기록 및 관리하고 보고서를 작성하는 작업이다.
(4) 형상 감사
베이스라인의 무결성을 평가하기 위해 확인, 검증 과정을 통해 공식적으로 승인하는
작업을 말한다.
3. 형상관리 구성
형상관리는 기준선(Baseline), 형상 항목(Configuration Item), 형상 버전(Configurat
ion Version), 형상 제품(Configuration Product)으로 구성된다.

2. 주요 소프트웨어 소스코드 관리도구의 사용 명령어
(1) SVN(Subversion) 관리도구의 주요 명령어
(가) checkout: 서버 저장소의 전체 프로젝트를 작업 사본으로 가져오는 명령어 (처음
내려받을 때 사용)
(나) update: 작업 사본을 최신 서버 버전으로 동기화하는 명령어
(다) add: 신규 파일을 버전관리 대상으로 등록하는 명령어로 등록 후 commit 해야 서
버에 반영됨
(라) commit: 작업 사본의 변경 내용을 서버 저장소에 반영 (comit 메시지를 입력함)
(마) status: 작업 사본과 저장소의 차이 상태를 표시하는 명령어로 작업 사본에서 변경
된 파일들의 상태를 확인 (수정, 추가, 삭제 등)
(바) revert: 작업 사본의 변경 내용을 취소하고, 마지막 업데이트 상태로 되돌림
(사) diff: 서버와 작업 사본, 또는 두 버전 간의 차이 등 파일 간 변경된 내용(차이점)을
비교하여 보여 주는 명령어를 확인할 때 사용하는 명령어
(2) Git 관리도구의 주요 명령어
(가) git init: 현재 디렉터리를 Git 로컬 저장소로 초기화하여 .git 디렉터리를 생성함
(나) git clone <URL>: 원격 저장소를 복제하여 로컬에 동일한 저장소를 새로 생성
(다) git add <파일명>: 수정/추가된 파일을 스테이징 영역에 추가
(라) git commit –m “메시지”: 스테이징 영역의 변경 사항을 로컬 저장소에 저장 (버전
생성)
(마) git status: 현재 작업 디렉터리의 변경 상태 및 스테이징 상태를 확인
(바) git branch: 브랜치 목록을 확인하며, 현재 활성화된 브랜치를 표시
(사) git branch <브랜치명>: 새로운 브랜치를 브랜치명으로 생성하는 명령어
(아) git fetch: 원격 저장소의 변경 사항을 로컬로 가져오되, 작업 브랜치는 변경하지 않음
(자) git merge <브랜치명>: 지정한 브랜치의 변경 사항을 현재 브랜치에 병합
(차) git pull: 원격 저장소의 변경 사항을 가져오고(fetch), 현재 브랜치에 병합
(카) git restore <파일명>: 해당 파일의 변경 내용을 마지막 커밋(commit) 상태로 되돌
리는 명령어. 이전의 git checkout 명령어와 동일한 기능
(타) git log: commit 이력을 확인
(파) git reset: 스테이징 또는 commit 상태를 이전으로 되돌림

소스코드 관리 지침은 소스코드 관리를 위해 역할별로 준수해야 할 내용이 기록된 지침
문서이다.
1. 소스코드 관리 지침의 목적
소스코드 관리 지침의 목적은 소스코드의 생성, 변경, 삭제 등 소스코드의 안전한 관리
를 위해 준수하여야 할 관리 방법을 정의함으로써 소스코드의 변경 사항 추적, 오류 복
구, 복원, 백업 등 정보 자산을 보호하는 데 있다.
2. 소스코드 관리 지침의 구성
소스코드 관리 지침의 구성은 소스코드 관리 지침의 목적, 적용 범위, 역할 및 책임,
소스코드 분류 체계, 소스코드 변경관리 방법 등의 내용으로 구성되어 있다.
(1) 소스코드 관리 지침 목적
소스코드 관리 지침 문서를 만드는 목적을 기술한다.
(2) 소스코드 관리 지침 적용 범위
프로젝트 유형, 소스코드 관리 대상자 구성에 따라 소스코드 관리 지침의 적용 범위
를 기술한다.
(3) 역할 및 책임
소스코드 관리 담당자의 역할을 분류하고 역할별 책임을 명시한다.
(4) 소스코드 관리 방법
소스코드 관리를 위해 사용할 소스코드 관리도구를 종류별로 명시하고 관리 방법에
대해 명시한다.
(5) 소스코드 분류 체계
소스코드 관리를 위하여 소스코드를 유형별로 분류 체계를 명시한다.
(6) 소스코드 변경관리
소스코드의 변경 사항 추적, 오류 복구 관리를 위하여 소스코드의 변경관리 절차 방
법에 대해 명시한다.
(7) 소스코드 복원 방법
소스코드의 오류 복구를 위하여 소스코드를 복원하는 방법에 대해 명시한다.
(8) 소스코드 백업 방법
소스코드의 안전한 관리를 위해 주기적으로 소스코드를 백업하는 방법에 대해 명시
한다.
(cid:49685) 버전관리 체계
1. 소프트웨어 버전 작성(Software Versioning)
소프트웨어 버전은 단순히 숫자를 나열하는 것이 아니라, 사용자와 개발자 간의 중요한
소통 수단이다. 버전 번호를 통해 소프트웨어의 변경 이력, 호환성 여부, 새로운 기능
추가, 버그 수정 등을 명확하게 전달할 수 있다. 일반적으로 널리 사용되는 표준은 유
의적 버전(Semantic Versioning, 줄여서 SemVer)이다. 이 규칙을 따르면 버전을 체
계적으로 관리하고, 의존성 문제를 해결하는 데 도움이 된다.
2. 소프트웨어 버전 작성 방법
유의적 버전(SemVer)의 핵심 규칙은 ‘MAJOR. MINOR. PATCH’ 세 부분으로 구성된
숫자 조합을 사용한다.
<표 1-4> 유의적 버전 작성 방법
예시: `1.4.2`
MAJOR (주 버전): 1
MINOR (부 버전): 4
PATCH (수 버전): 2
3. 소프트웨어 버전 작성 규칙
소프트웨어 버전은 다음 규칙에 따라 변경한다. 상위 버전이 올라가면, 하위 버번은 0
으로 초기화해야 한다.
(1) Major 버전
Major 버전은 API가 이전 버전과 호환되지 않는 변경(Breaking Change)이 있을
때 버전을 올린다. MAJOR 버전을 올리면, MINOR와 PATCH 버전은 반드시 0으
로 초기화한다.
<표 1-5> Major 버전 변경 이유와 규칙
주 변경 사유 규칙
(cid:49746)함수 이름이 변경된 경우 (run_analysis() -> run())
(cid:49746)함수의 필수 파라미터가 추가되거나 삭제된 경우 1.7.2 -> 2.0.0 (O)
(cid:49746)기존 기능이 완전히 삭제된 경우 1.7.2 -> 2.1.0 (X)
(cid:49746)소프트웨어의 핵심 아키텍처가 변경된 경우
(2) Minor 버전
Minor 버전은 이전 버전과 호환되는 방식으로 새로운 기능이 추가될 때 버전을 올
린다. Minor 버전이 오르는 것은 새로운 기능이 생겼지만, 기존 기능은 문제없이
그대로 사용할 수 있다는 의미이다.
<표 1-6> Minor 버전 변경 이유와 규칙
주 변경 사유 규칙
(cid:49746)새로운 함수나 클래스가 추가된 경우
(cid:49746)기존 함수에 선택적(optional) 파라미터가 추가된 경우 1.7.2 -> 1.8.0 (O)
(cid:49746)사용 중단(deprecated)될 기능이 표시되었지만 아직 삭 1.7.2 -> 1.8.3 (X)
제되지는 않은 경우
(3) Patch 버전
Patch 버전은 이전 버전과 호환되는 방식으로 버그나 오류가 수정되었을 때 올린
다. Patch 버전을 올리는 것은 기능 변경은 없으며, 내부적인 문제만 고쳤다는 의
미이다.

계임을 나타내기 위해 MAJOR 버전을 0으로 사용한다.

개발 환경 백업
•응용소프트웨어 개발을 위하여 구축된 개발 환경에 대한 백업 작업 내용을 식별할 수 있다.
학습 목표
•수립된 개발 환경의 백업 작업 일정에 따라 백업을 수행할 수 있다.
필요 지식 /
(cid:49684) 백업의 개념과 필요성
소프트웨어 개발 환경을 안정적으로 운영하고 예기치 않은 사고로부터 보호하기 위해서는
백업과 복원(복구)은 필수적이다. 개발 환경 백업이란 응용소프트웨어를 개발·운영하는 데
필요한 모든 환경과 데이터를 안전하게 저장하는 과정을 말한다. 개발 환경에는 소스코드,
데이터베이스, 서버 설정, 외부 라이브러리, 빌드 도구, 문서 등 다양한 요소가 포함된다.
이러한 개발 환경은 시간이 지나면서 계속 변경되며, 변경 과정에서 오류가 발생하거나 예
상치 못한 장애가 생길 수 있다. 예를 들어 프로그래밍 중 실수로 중요한 코드를 삭제하거
나, 서버 하드디스크가 고장 나는 경우, 또는 랜섬웨어 공격으로 데이터가 암호화되는 경
우에 대비해서 백업을 실시한다.
1. 백업(Backup)
백업은 특정 시점의 데이터 또는 시스템의 상태를 그대로 복사하여 별도의 저장 매체
에 보관하는 행위 또는 그 결과물(복사본)을 의미한다. 이는 단순한 파일 복사를 넘어,
시스템의 설정, 데이터베이스의 내용, 사용자 정보 등 유무형의 자산을 보호하기 위한
가장 기본적인 정보보호 활동이다.
2. 복원(Restore)
복원은 백업해 둔 데이터 사본을 사용하여 특정 시점의 상태로 시스템이나 데이터를
되돌리는 과정을 의미한다. 백업의 궁극적인 목표는 성공적인 복구를 통해 서비스를 신
속하게 정상화하는 것이다.

2. 백업 정책
백업 실행은 cron(리눅스), 작업 스케줄러(윈도우)를 이용한 스크립트 실행이 가장 기본
적인 방법이다. Jenkins 같은 CI/CD 도구나 AWS Backup, Azure Backup 같은
클라우드 네이티브 서비스를 사용할 수도 있다.
백업 정책은 다양한 요소들을 종합하여 조직의 상황에 맞게 문서화해야 한다. 이때 일
반적으로 데이터 보호를 위한 업계 표준인 ‘3-2-1 규칙’을 따른다.

3. 복원(복구) 절차 수립 및 백업 테스트
백업은 복원(복구)가 이루어지지 않으면 의미가 없다. 누가, 어떻게, 어떤 순서로 복구
를 진행해야 하는지 명확한 절차를 문서로 만들어야 한다. 해당 문서를 기반으로 분
기별 또는 반기별로 실제 백업 데이터로 복구를 시도하는 장애 대응 훈련을 실시해야
한다. 이를 통해 백업 데이터의 유효성을 검증하고, 복구 절차의 문제점을 개선할 수
있다.
자세한 복원 절차는 ‘학습 3. 개발 환경 복원하기’를 통해 학습할 수 있다.

(cid:49686) 데이터베이스 백업(Oracle 중심)
오라클(Oracle)의 표준 유틸리티인 Data Pump(‘expdp’)를 사용하여 system 사용자가
소유한 모든 테이블과 데이터를 백업한다.
1. Oracle 백업 디렉터리 설정
Data Pump는 보안상의 이유로 서버에 미리 지정된 폴더에만 백업 파일을 생성할 수
있다. 이 설정을 위해 최초 1회만 수행하며, 관리자 계정(SYS)의 권한이 필요하다.
(1) 백업용 폴더 생성
예) E:\dev_backup\oracle_backup
(2) 계정에 권한 부여
명령 프롬프트(cmd)를 열고 sys 계정으로 오라클에 접속한다. sys 계정의 암호는
Oracle 설치 시 부여한 암호이며, 실습에서는 암호를 1234로 가정한다.
C:\> sqlplus sys as sysdba
Enter password: 1234
1. ‘backup_dir’라는 이름으로 Oracle 디렉터리 객체를 생성
(실제 경로는 E:\dev_backup\oracle_backup)
SQL> CREATE OR REPLACE DIRECTORY backup_dir AS 'E:\dev_backup\oracle_backup';
Directory created.
2. 백업할 사용자(system)에게 해당 디렉터리 객체에 대한 읽기/쓰기 권한 부여
SQL> GRANT READ, WRITE ON DIRECTORY backup_dir TO system;
Grant succeeded.
3. 종료
SQL> EXIT;
2. Data Pump Export 실행
system 계정의 데이터베이스를 백업을 수행한다. system의 암호는 1234로 가정한다.
명령프롬프트(cmd)에서 직접 실행해야 하며, [그림 2-11]과 같이 한 줄 명령어이지만
“^” 기호를 사용하면 여러 줄로 입력하여 사용할 수 있다.
C:\> expdp system/1234@xe ^
SCHEMAS=system ^
DUMPFILE=system_db_backup.dmp ^
LOGFILE=system_db_backup.log ^
DIRECTORY=backup_dir
• system/1234@xe: 접속 정보 (사용자명/비밀번호@SID)
• SCHEMAS=system: system 사용자가 소유한 모든 객체를 백업 대상으로 지정
• DUMPFILE: 백업 데이터가 저장될 파일명
• LOGFILE: 백업 과정이 기록될 로그 파일명
• DIRECTORY: 앞 단계에서 생성한 Oracle 디렉터리 객체 이름

(cid:49685) 백업 수행 결과를 보고한다.
개발 환경의 백업이 정상적으로 수행되었는지 백업 운영자는 백업 운영 팀장에게 수행 결
과를 보고한다.
백업 현황 및 백업 소요 시간, 백업 용량 등을 주기적으로 통계 분석 하여, 사전에 백업
시스템의 증설 및 신규 구축 계획을 수립하여야 한다.
백업 수행 결과는 아래와 같이 일간 및 월간, 연간 수행 결과 보고서를 작성한다(활용 서
식 ‘백업 일일 보고서’ 참조).
1. 일간 수행 결과 보고서를 작성한다.
백업 운영자는 백업 계획서에 따라 정기 및 비정기 백업을 수행하고, 백업 수행 결과를
매일 백업 운영 팀장에게 보고하고 관련 조직에게 통보하여야 한다.
2. 월간 수행 결과 보고서를 작성한다.
당월 수행한 총 백업 건수 및 백업 용량, 백업 시스템 변경 사항, 백업 에러 및 조치
사항, 백업 계획서 변경 여부, 백업 추이에 따른 증설 검토 여부 등을 매월 통계 분석
하여 백업 운영 팀장에게 보고한다.
3. 연간 수행 결과 보고서를 작성한다.
백업 운영자는 연간 백업 계획서를 작성하고 시스템이 추가 또는 폐기되는 변동 사항
을 백업 운영 팀장에게 보고한다. 백업 운영 팀장은 주기적으로 백업 계획서를 작성하
여 시스템의 증설 및 신규 구축 계획을 수립하여 예산에 반영한다.
수행 tip
•백업 요청서에 의해 백업한 내용을 점검하는 절차를 학
습함으로써 백업 결과를 이해할 수 있도록 한다.
•일일, 월간, 연간 백업 보고서를 스스로 작성함으로써
백업 시 중요한 사항에 관해 확인하고 보고 체계에 대
해 이해할 수 있도록 한다.

를 최소화’하는 것이다. 복원의 핵심 목표는 다음과 같다.

[그림 3-10] 복원한 프로젝트 확인
(cid:49686) 데이터베이스를 복원한다.
Oracle DB에 impdp를 사용해서 복원하는 실습을 수행한다.
실습 시나리오
개발자가 실수로 애플리케이션이 사용하는 핵심 유저/스키마인 MYAPP_USER 계정을 DROP
USER ... CASCADE 명령으로 삭제했다. 데이터베이스 자체는 정상 작동하지만, 애플리케이션과
관련된 모든 테이블, 데이터, 객체를 복원해야 한다. expbp로 백업한 자료는 다음과 같다.
백업 파일 위치: E:\dev_backup\oracle_backup
백업 파일 명: MYAPP_USER_BACKUP.dmp
1. 백업 파일 준비 및 Oracle 디렉터리 객체를 확인한다.
expdp(백업), impdp(복원) 명령어는 명령프롬프트(cmd) 명령어이다. expdp, impdp
는 로컬 파일 시스템 경로를 직접 사용하지 않고, 데이터베이스에 생성된 디렉터리 객
체(Directory Object)를 통해 파일에 접근한다.
C:\> sqlplus system/1234
-- 'BACKUP_DIR' 라는 이름의 디렉터리 객체를 생성
SQL> CREATE OR REPLACE DIRECTORY BACKUP_DIR AS 'E:\dev_backup\oracle_backup';
-- system 객체에 디렉터리 객체에 대한 읽기, 쓰기 권한 부여
SQL> GRANT READ, WRITE ON DIRECTORY BACKUP_DIR TO system;
2. 복구할 유저 및 테이블 스페이스 사전을 생성한다.
impdp가 유저를 자동으로 만들 수도 있지만, 권한이나 테이블 스페이스 문제를 피하
기 위해 미리 생성한다. 복원할 MYAPP_USER를 생성한다. 암호는 1234로 지정한다.
-- 삭제된 MYAPP_USER 유저를 다시 생성
-- USERS, TEMP는 기본 테이블 스페이스 이름이며 환경에 따라 다름
SQL> CREATE USER MYAPP_USER IDENTIFIED BY 1234
DEFAULT TABLESPACE USERS
TEMPORARY TABLESPACE TEMP;
-- 유저에게 기본적인 접속 및 리소스 생성 권한 부여
SQL> GRANT CONNECT, RESOURCE TO MYAPP_USER;
SQL> exit;
3. impdp 명령어로 데이터 임포트를 실행한다.
관리자 권한으로 명령 프롬프트(cmd)를 열고 impdp 명령을 실행하여 데이터를 복원
한다. ‘impdp system/password ~ SCHEMAS=MYAPP_USER’까지 한 줄로 입력하는 명
령어이며, 다음과 같이 문장 끝에 “^” 기호를 사용할 경우 여러 줄로 나누어서 사용할 수
있다.
C:\> impdp system/1234 ^
DIRECTORY=BACKUP_DIR ^
DUMPFILE=MYAPP_USER_BACKUP.dmp ^
LOGFILE=impdp_log.log ^
SCHEMAS=MYAPP_USER
* system/1234: impdp를 실행할 권한이 있는 유저 정보
* DIRECTORY=BACKUP_DIR: 1단계에서 생성한 Oracle 디렉터리 객체 이름
* DUMPFILE=MYAPP_USER_BACKUP.dmp: 복원에 사용할 덤프 파일 이름
* LOGFILE=impdp_log.log: 임포트 과정 전체가 기록될 로그 파일 이름
* SCHEMAS=MYAPP_USER: 덤프 파일 내용 전체가 아닌, MYAPP_USER 스키마에 해
당하는 부분만 임포트
4. 로그 파일 확인 및 복구 상태를 확인한다.
임포트 작업이 완료되면, 생성된 로그 파일(impdp_log.log)을 열어 ‘Job ... successfully
completed’ 메시지가 있는지 확인하고, 혹시 오류나 경고 메시지가 없었는지 확인한
다. 그리고 다음과 같이 복구가 되었는지 확인한 후 애플리케이션(JSP 프로젝트)을 재
시작하고, 데이터베이스와 연동하여 기능이 정상적으로 동작하는지 최종 확인한다.
SQL*Plus 또는 SQL Developer로 복구된 ‘MYAPP_USER’ 계정으로 접속한다.
C:\> sqlplus MYAPP_USER/1234
-- 테이블 목록을 조회하여 객체들이 정상적으로 복원되었는지 확인한다.
SQL> SELECT table_name FROM user_tables;
-- 백업 시점에 존재했던 테이블 목록이 모두 표시되어야 한다.
-- 핵심 테이블의 데이터 건수를 확인하여 데이터까지 복원되었는지 검증한다.
SQL> SELECT COUNT(*) FROM products;

웹서버 및 데이터베이스 등 개발 환경의 복원이 정상적으로 수행되었는지 업무 담당자는 시
스템의 정상 실행 여부를 확인한 후 시스템의 실행 상태를 업무 팀장에게 보고한다.
1. 개발 환경의 시스템이 정상적인지 확인한다.
재시작한 개발 환경의 시스템이 정상적으로 실행이 되는지 확인한다.
웹사이트에 접속하여 정상적으로 요청한 버전으로 복원되었는지 확인한다.
2. 개발 환경의 시스템 상태가 비정상이면 백업 담당자에게 복원을 재요청한다.
업무 담당자는 시스템의 상태가 정상이면 복원 수행 결과에 대해 업무 팀장에게 보고
한다. 시스템의 상태가 비정상이면 업무 담당자와 업무 팀장은 복원 요청서를 작성하여
백업 담당자에게 복원을 재요청한다. 시스템이 정상적으로 실행될 때까지 이 과정은 반
복된다.
3. 복원 수행 결과를 유관 부서에 보고한다.
업무 팀장은 관련된 부서에 개발 환경이 정상적으로 복원되었음을 알리고 문제 원인과
조치 사항에 대해 공유한다.

교수 방법
• 복원의 개념, 다양한 복원 방법, 복원 절차 등을 PPT로 제시하고 설명하여 학습자들이
복원에 대한 중요성을 학습할 수 있도록 설명한다.
• 백업한 개발 환경과 데이터베이스를 기준으로 복원 지침을 작성하여 학습자들이 백업된
환경으로 복원을 수행할 수 있도록 지도한다.
• 복원 대상 및 복원 지점 식별, 복원 수행 등 복원을 위한 전 주기의 절차를 학습자들이
역할을 나누어 실습할 수 있도록 지도한다.
• 복구 목표 시점, 복구 목표 시간을 PPT로 제시하여 학습자들이 영향도와 긴급도에 대
해 이해하고 영향도와 긴급도를 기준으로 장애 등급을 분류할 수 있도록 지도한다.
• 개발 환경의 복원 결과를 점검하기 위해 컨테이너 기반 도구 사용법, 데이터베이스
SQL 문장을 사전에 학습시켜 복원된 결과를 점검할 수 있도록 지도한다.
학습 방법
• 복원에 대한 개념에 대해 이해하고 다양한 복원 방법에 따라 복원 수행 방법이 다른 점
을 인지하고 상황별로 복원할 수 있도록 학습한다.
• 교수자가 제시하는 복원 지침을 기준으로 복원 절차를 수행함으로써 주기적인 백업 결
과가 중요함을 파악한다.
• 교수자가 제시하는 복원 절차에 따라 구성된 역할에 따라 복원을 수행함으로써 역할별
로 다른 복원 작업을 학습하여 각자 역할의 중요성을 파악한다.
• 영향도와 긴급도에 대해 파악하고 이를 기반으로 복원 지점을 식별할 수 있도록 학습한다.
• 복원 결과가 정상적인지 점검하기 위한 컨테이너 기반 도구와 데이터베이스 SQL 문장
의 종류 및 사용법에 대해 학습한다.
